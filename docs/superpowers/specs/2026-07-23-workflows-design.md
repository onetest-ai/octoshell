# Workflows as a board entity

**Date:** 2026-07-23
**Status:** approved, ready for planning

## Problem

The Octobots board says *what* work exists (campaigns → missions → tasks, plus bugs) but nothing
about *how* it gets executed: in what order, by which agents, what runs in parallel, where the
gates are. Today the closest thing is **teams** — a `.octobots/teams/<id>.json` naming a backend and
a flat roster of roles, bound to a scope through a VS Code `globalState` map. Teams answer "who"
with no ordering, no per-mission shape, and no on-disk binding.

We want a **workflow**: a board unit that plans the order of execution and the agents to be called,
readable as a diagram in the extension and executable by a CLI coding agent.

## Solution overview

A workflow is a fifth folder-backed board entity, parented by **either** a campaign or a mission
(the same either/or parentage `Bug` already has). It has two faces:

- **`workflow.js`** — the source of truth. A **Claude Code dynamic-workflow script**: it exports a
  pure-literal `meta` object and a free-form body using `agent()` / `parallel()` / `pipeline()` /
  `phase()`. Claude Code's `Workflow` tool runs it. Nothing in the extension executes it.
- **`workflow.md`** — the human/board face. A managed brief (heading, `## Description`, `## Runs`,
  boundary comment, agent-owned `## Notes` tail). Like every other entity it is identified by
  `folder:<relFolderPath>`; no id marker is written into the file.

The extension **reads** `meta` to draw a diagram and **edits** `meta` through a structured list
editor. It never interprets the script body.

Levels are independent, not inherited:

- a **campaign** workflow orchestrates **missions**;
- a **mission** workflow orchestrates **tasks**.

A campaign may hold several workflows (a library). A mission has at most one.

## On-disk layout

```
.octobots/campaigns/<campaign-slug>/
  campaign.md
  workflows/
    <workflow-slug>/
      workflow.md
      workflow.js
  missions/<mission-slug>/
    mission.md
    workflows/
      <workflow-slug>/
        workflow.md
        workflow.js
```

`workflow.md`:

```markdown
# <Workflow name>

## Description
<one paragraph>

## Runs
- [status:done] 2026-07-23 — 4 agents, 12m
- [status:failed] 2026-07-22 — review phase

<!-- Auto-generated by Octobots ... -->
## Notes
<agent-owned free text>
```

`workflow.js`:

```js
export const meta = {
  name: 'build-tasks',
  description: 'Drive each task on the mission to a merged, verified PR',
  phases: [
    { title: 'Plan', steps: [
        { id: 's1', agent: 'octobots-planner', label: 'Decompose mission' } ] },
    { title: 'Build', steps: [
        { id: 's2', agent: 'implementer', label: 'Build task',  parallel: 'b' },
        { id: 's3', agent: 'tester',      label: 'Write tests', parallel: 'b', backend: 'codex' } ] },
    { title: 'Review', steps: [
        { id: 's4', agent: 'reviewer', label: 'Code review', dependsOn: ['s2', 's3'] } ] },
  ],
}

phase('Build')
const results = await pipeline(tasks,
  t => agent(`implement ${t.id}`, { phase: 'Build' }),
  r => agent(`review ${r}`,       { phase: 'Review' }))
```

## Model (`packages/board`)

```ts
export interface WorkflowStep {
  id: string;            // unique within the workflow
  agent: string;         // agent / subagent type to call
  label: string;         // node caption
  parallel?: string;     // steps sharing a group id run concurrently
  dependsOn?: string[];  // step ids
  backend?: string;      // claude | copilot | codex — carried over from teams
}

export interface WorkflowPhase {
  title: string;
  detail?: string;
  steps: WorkflowStep[];
}

export interface Workflow {
  id: string;
  campaignId: string | null;   // exactly one of campaignId / missionId is set
  missionId: string | null;
  name: string;                // meta.name
  description: string;         // meta.description
  phases: WorkflowPhase[];
  scriptPath: string;          // <folderPath>/workflow.js
  folderPath: string;
  parseError: string | null;   // non-null when meta could not be read
  lastRunStatus: string | null; // newest `## Runs` board line, or null
  createdAt: number;
  updatedAt: number;
}

export type WorkflowParent = { campaignId: string } | { missionId: string };
```

`BoardModel` gains `listWorkflows(parent)`, `getWorkflow(id)`, `workflowIdByFolderPath(path)`, and
indexes `workflowsByCampaign` / `workflowsByMission` / `workflowByFolder`, all cleared and rebuilt
in `rebuild()` like every other entity.

### Reading `meta` without executing the script

`BoardModel` must not import or run `workflow.js` — it is arbitrary code, it is ESM, and parsing
happens on every board rebuild. Instead:

1. Locate the `export const meta = {` … matching-close-brace span by scanning for balanced braces
   outside string literals and comments.
2. Evaluate **only that object literal** with `node:vm`:
   `vm.runInNewContext('(' + literal + ')', Object.create(null), { timeout: 50 })`.
   The Workflow contract guarantees `meta` is a pure literal, so a call, identifier, spread or
   template interpolation resolves to nothing in the empty context and throws — it cannot run.
3. Schema-check the result into `WorkflowPhase[]`. Unknown keys are preserved-but-ignored so a
   script can carry `model`, `effort`, `whenToUse` etc. without the parser rejecting it.

Any failure at any step sets `parseError` and leaves `phases` empty. The workflow still appears on
the board, flagged in the tree and in the panel — an unreadable workflow must be visible, not
invisible.

### Writes (`write.ts`)

- `createWorkflow(parent, { name })` — creates the folder, a managed `workflow.md`, and a
  `workflow.js` scaffold containing a valid single-phase `meta` and an empty body.
- `updateWorkflow(id, { description })` — edits `workflow.md` fields only.
- `deleteWorkflow(id)` — removes the folder.
- `appendWorkflowRun(id, { status, summary, at })` — appends one board line under `## Runs`.
- `setWorkflowMeta(id, meta)` — re-serializes the meta object as a formatted literal and replaces
  **only the located span** in `workflow.js`. The script body is left byte-identical. This is the
  single operation that lets the UI editor write back without touching the user's code.

`## Runs` reuses the existing board-line format (`- [status:done] …`) and is read with the existing
`parseSectionBoardStatuses` helper — no new parsing machinery. The pack appends entries during
execution; the extension only reads them.

### Validation (`packages/board/validate.ts` and the pack's `validate.js`)

Errors:

- `workflow.js` missing, or `export const meta` absent or unparseable
- `meta.name` does not match the workflow folder slug
- no phases, or a phase with no steps
- a step missing `id`, `agent` or `label`
- duplicate step id within a workflow
- `dependsOn` referencing an unknown step id
- a `parallel` group whose members span more than one phase
- a mission with more than one workflow

Warning:

- a `phase('X')` call in the script body with no matching `meta.phases` entry (cheap regex scan)

## Extension host

- **`BoardHost`** — workflow CRUD mirroring the existing entity methods; every mutation writes
  markdown/script, reconciles a fresh `BoardModel`, and emits `entities:changed`.
- **`CampaignsTree`** — workflow nodes under campaigns and under missions, using the fixed codicon
  **`circuit-board`** (unused by the existing `milestone` / `target` / `checklist` / `bug`
  vocabulary), tinted by `lastRunStatus` through the existing `statusColor` map.
- **`EntityPanelManager`** — a `workflow` panel kind alongside campaign/mission/task/bug.
- **RPC** (`rpc-contract.ts` + `rpc-dispatcher.ts`) — `workflow:list`, `workflow:get`,
  `workflow:create`, `workflow:update`, `workflow:delete`, `workflow:setMeta`,
  `workflow:openScript`.
- **Commands** — `octoshell.newWorkflow`, `octoshell.deleteWorkflow`, with the usual tree context
  menu entries.

There is **no run trigger in the extension**. Execution is Claude Code's `Workflow` tool, invoked by
the `mission-execution` skill.

## Webview — `WorkflowView`

Two panes.

**Diagram (read-only).** Hand-rolled SVG, no new dependency, drawn directly from `phases`. One
horizontal band per phase; steps laid out left-to-right within a band; a `parallel` group drawn as a
split/join; `dependsOn` drawn as edges. Colors come from the existing CSS-variable VS Code theme
tokens, so it themes for free. Mermaid was rejected: heavy dependency, and it fights VS Code
theming.

**Editor.** A structured list beside the diagram: phases with their steps (agent, label, parallel
group, dependsOn, backend), add / remove / reorder. Every change round-trips through
`workflow:setMeta`. Plus the `workflow.md` description field, a read-only Runs list, and an
"Open script" action that opens `workflow.js` in a normal editor tab for body edits.

When `parseError` is set the editor is replaced by the error and the "Open script" action — the UI
must never attempt to rewrite meta it could not read.

## Removals

Two concepts leave the product in the same change.

### Customizations

Not needed. Delete:

- `packages/customizations` (whole package, plus its workspace/turbo references)
- `apps/vscode-extension/src/host/customizations-io.ts`, `customizations-tree.ts`
- the `octoshell.customizations` view contribution, the `octoshell.addCustomization` command and its
  `view/title` menu entry
- `customizations:*` RPC methods, contract entries, and `octoshell.customizations` shim methods
- `BoardHost.listCustomizations()`
- `test/customizations-io.test.ts`, `test/customizations-tree.test.ts`
- README / CLAUDE.md references

### Teams

Workflows subsume them — a step names its agent directly, and `backend` survives as an optional
per-step field. Delete:

- `apps/vscode-extension/src/host/team-assignments.ts`
- `apps/vscode-extension/src/webview/team-section.tsx` and its use in `campaign-view` / `mission-view`
- `teams:list`, `campaign:setTeam`, `mission:setTeam`, `team:getBinding`, `team:setBinding`,
  `team:assign`, `team:assignments` RPC methods plus `TeamEntry` / `TeamBinding` /
  `TeamTypeAssignment` contract types and shim methods
- `BoardHost.listTeams()` / `setTeam()` / `getTeamBinding()` / `setTeamBinding()`
- `teamId` from `Campaign` and `Mission` in `packages/board/src/types.ts`
- the pack's `scripts/create-team.js` and the **Teams** section of `mission-planner/SKILL.md`

`.octobots/teams/*.json` files in existing workspaces are simply ignored after this change; nothing
migrates them.

## Workflow pack (v22)

- New scripts: `add-workflow.js` (scaffold folder + md + js), `set-step.js` (edit a step in `meta`),
  `add-run.js` (append a `## Runs` line). `list.js`, `show.js` and `validate.js` extended to cover
  workflows.
- `mission-planner/SKILL.md` — a **Workflows** section replacing **Teams**: the two levels, the
  `meta` schema, the rule that `meta` must stay a pure literal and must describe every phase the
  body enters, and the one-workflow-per-mission rule.
- `mission-execution/SKILL.md` — read the mission's workflow, call
  `Workflow({ scriptPath: '.octobots/…/workflow.js' })`, then append a run entry with `add-run.js`.

## Testing

- `packages/board` — meta extraction (well-formed, braces inside strings, comments, missing export,
  non-literal meta, timeout), schema coercion, `BoardModel` rebuild over fixture trees with campaign
  and mission workflows, `setWorkflowMeta` body preservation, `appendWorkflowRun`, every validate
  rule.
- Host — RPC exhaustiveness test (already exists) covers the new methods; tree and panel-manager
  tests for workflow nodes; temp-dir CRUD tests for `BoardHost`.
- Webview — `WorkflowView` renders a diagram for a multi-phase parallel workflow, renders the
  parseError state, and round-trips a step edit through `workflow:setMeta`.
- Removals — delete the customizations/teams tests rather than adapting them.

## Sequencing

1. **Removals** — customizations + teams. Pure deletion; the repo stays green throughout.
2. **`packages/board`** — types, meta parser, `BoardModel`, `write.ts`, `validate.ts`, tests.
3. **Host** — `BoardHost`, tree, panel manager, RPC contract + dispatcher, commands.
4. **Webview** — `WorkflowView`: diagram + structured editor.
5. **Pack v22** — scripts and doctrine.

Order matters: `packages/board` must be built before the extension typechecks against its new
public types (downstream reads `dist/`, not source).
