# Octobots Workflow

Octobots organizes work as **campaigns → missions → tasks**. Each lives as a **YAML**
"board" file under `.octobots/`, and **the `.octobots/` tree is the source of truth** —
editing those files (via these scripts) is how you drive Octobots; the app reads them
live. You do not call an API. Each entity is a **folder** (`campaign.yaml` / `mission.yaml` /
`task.yaml` / `bug.yaml`) and is identified by its **folder path** — no id marker is written into
the file. The scripts create those folders — `add-campaign.js`, `add-mission.js`, `add-task.js`,
`add-bug.js`, one per level.

**Children are folder-derived, never enumerated in the parent.** A campaign's missions, a
mission's tasks, and a parent's bugs are discovered by scanning the `missions/` / `tasks/` /
`bugs/` sub-folders — a `campaign.yaml` NEVER lists its missions, a `mission.yaml` NEVER lists its
tasks or bugs. `status`, `role`, and `severity` live as **fields in the child's own YAML**, not as
markers on any parent line. There is no `## Missions` / `## Tasks` / `## Bugs` projection section
anymore, and no board line to hand-add — always use the `add-*` scripts, which create the child
folder and its YAML.

## Layout

```
.octobots/campaigns/<campaign-slug>/campaign.yaml
.octobots/campaigns/<campaign-slug>/missions/<mission-slug>/mission.yaml
.octobots/campaigns/<campaign-slug>/missions/<mission-slug>/tasks/<task-slug>/task.yaml
.octobots/campaigns/<campaign-slug>/bugs/<bug-slug>/bug.yaml            # or under a mission
.octobots/campaigns/<campaign-slug>/missions/<mission-slug>/bugs/<bug-slug>/bug.yaml
```

Your working directory is the repo root, so these are real relative paths.

## Board anatomy

Every entity is a single `<kind>.yaml` file carrying **only its own fields** — no managed
header, no agent-owned tail, no `Auto-generated by Octobots` comment (those existed to protect the
old Markdown from hand-editing; YAML fields don't need them). Keys are `snake_case` on disk.

Example `mission.yaml`:

```yaml
name: M3 - Skills workspace
status: draft
description: |
  One-paragraph (or multi-line) description of the mission.
acceptance_criteria:
  - text: a concrete, checkable criterion
    done: false
  - text: a criterion already met
    done: true
documents:
  - label: M3 plan
    target: docs/superpowers/plans/2026-06-15-foo.md
tokenomics:
  effort_days: 3
  size_tshirt: M
  complexity_score: 18
notes: |
  ## Decision
  Auth uses the server clock, not the client — multilateration needs a single time base.
  Signed off by the product owner on 2026-07-01.
```

Fields, by kind:
- **campaign.yaml** — `name`, `status` (settable; a non-`draft` value overrides the mission
  rollup), `target`, `description`, `acceptance_criteria[]`, `documents[]`, optional `notes`.
- **mission.yaml** — `name`, `status`, `description`, `acceptance_criteria[]`, `documents[]`,
  optional `tokenomics`, optional `notes`. (Mission status is driven by the app run lifecycle + task
  rollup — see *Setting status on a mission* below.)
- **task.yaml** — `name`, `status`, optional `role`, `description`, `acceptance_criteria[]`,
  optional `tokenomics`, optional `notes`.
- **bug.yaml** — `name`, `status`, `severity`, `description`, `steps_to_reproduce`, `expected`,
  `actual`, `rca`, `environment`, optional `notes`.
- `acceptance_criteria` is a list of `{ text, done }`; `documents` is a list of `{ label, target }`;
  `tokenomics` is an open map (any `effort_days`/`size_tshirt`/`complexity_score`/`maturity`/… keys);
  `notes` is free-form prose (see below).

### Recording decisions & sign-offs — the `notes` field

As work proceeds, agents (and people) accumulate things that belong **with the entity** but aren't a
criterion, a document, or a status: a **recorded decision** and its rationale ("auth uses the server
clock because…"), an **update** on what changed and why, a **product-owner sign-off**. Put them in
the entity's **`notes`** field — a free-form block scalar (`notes: |`), preserved verbatim and shown
read-only under a **Notes** heading on the entity's panel (campaign, mission, task, and bug all have
one). Use your own `##`-style sub-headings inside it (`## Decision`, `## Update`, `## Product
decisions`) to keep it legible.

`notes` is the durable home for this. Don't leave a decision only in chat (it's gone when the chat
is) or only in a commit message (invisible from the board) — if it's a decision or sign-off about the
work, it belongs in `notes` on the entity it's about, where the next agent to open the board will see
it. Attach longer artifacts as **documents** instead; `notes` is for the short prose that explains
*why the work is what it is*.

**What a write preserves.** Every script rewrites the whole `<kind>.yaml` from the parsed fields,
but the parser carries through anything it does not model: unknown top-level keys, extra keys on an
acceptance criterion or a document link, nested blocks inside `tokenomics`, and `notes`. So you can
annotate an entity with your own keys and an unrelated `set-status.js` will not eat them. A key the
schema knows but the kind does not own (a `documents:` on a task, say) is also kept, and
`validate.js` reports it as misplaced so it gets moved rather than quietly ignored forever.

**Always edit through the scripts** (`set-criterion`, `set-status`, `add-doc`, …) — never by
appending text to a `<kind>.yaml`. Each script re-serialises the whole file from the parsed fields,
so an edit that appends raw text is either overwritten by the next script run or, worse, lands under
the wrong key: acceptance criteria appended as prose end up inside `notes` ("stranded criteria"),
where they look right to a reader but the board never counts them as criteria. `validate.js` fails
an entity whose `notes` contain criterion-shaped `- [ ]` lines and tells you to move them with
`set-criterion.js`. If you must edit by hand, keep the field names and nesting exactly as above and
run `validate.js` afterwards.

## Planning by scope

Which board you plan against — and how — depends on the scope you were asked about: a campaign, a
mission, or a single task. Work out which from the request and the board you were pointed at, then
follow the matching doctrine below.

### Campaign chat — orchestrator (strategic)

You turn an intent into a **campaign** and its **missions**. Think top-down: outcome → missions
→ acceptance criteria. You do NOT break missions into individual tasks — that is the planner's job.

1. Clarify the campaign outcome with the user — one focused question at a time when something is
   genuinely ambiguous; otherwise propose and proceed.
2. Decompose the outcome into a small set of missions, each independently shippable and each with
   explicit acceptance criteria.
3. Create each mission with `add-mission.js <campaign-dir|campaign.yaml> "M<n> - <Mission name>"`
   (and `--description "<one-line description>"`) — a sequential id (`M1`, `M2`, …), a descriptive
   name (the ` - ` after the id stays in the title). The script writes the mission folder + its
   `mission.yaml`; the campaign is not touched (missions are folder-derived). Creating the campaign
   itself is `add-campaign.js "<name>"`. If you are only *proposing* missions for the user to
   approve before creating, list them in chat rather than creating folders — nothing is on the
   board until you run `add-mission.js`.
4. If the campaign is backed by a design **spec** (e.g. a `superpowers` spec under
   `docs/superpowers/specs/`), record it as a document — see **Documents** below. Don't leave the
   spec linked only in chat; an unlinked spec is lost work when the chat is gone.
5. Run `validate` and fix any well-formedness errors before you finish.

Principles: YAGNI — propose the fewest missions that achieve the outcome. Every mission has at
least one acceptance criterion. Keep missions independent; if two must happen in a fixed order,
say so explicitly. Stay at strategic altitude — leave task decomposition to the planner.

### Mission chat — planner (tactical)

You break a **mission** into executable **tasks**. Work within the mission's scope; you do NOT
create or re-scope campaigns (that is the orchestrator's job).

1. Read the mission board to understand its scope and acceptance criteria.
2. Decompose into tasks that are each small, independently verifiable, and ordered only where a
   real dependency exists.
3. Create each task with `add-task.js <mission-dir|mission.yaml> "<title>" --description "<scope>"`
   (it writes the `tasks/<slug>/task.yaml` folder; the mission is not touched), then attach
   acceptance criteria with `set-criterion` on that `task.yaml`. **Always pass `--description`** —
   a task created with an empty description is not done being planned.

**Task contract (required):**
- **Id + descriptive name.** Title every task as `<id> - <descriptive name>`: a short hierarchical
  id, then a real name — e.g. `T3.1 - Add JWT validation to the /login endpoint`. The id is a stable,
  human-readable handle (so a person or the model can say "do T3.1"); the name says what the task
  accomplishes. A **bare id with no name** (`T1`, `T5.5`) is rejected, and so is an undescriptive
  name. Use a literal ` - ` (space-hyphen-space) between id and name — the parser keeps it as one
  title (only an em-dash ` — ` or a colon starts an inline description).
- **A real description — the scope of work.** Every task carries a `description` that says **what
  this task covers and what "done" looks like**: the concrete work (which files/endpoints/behaviour),
  the approach where it isn't obvious, and — just as important — what is **out of scope** so the next
  agent doesn't wander. The title is a handle, not a spec: `T3.1 - Add JWT validation` tells the
  executor almost nothing, while a description ("validate the `Authorization: Bearer` token on
  `/login` and `/refresh`; reject expired or tampered tokens with 401; reuse the existing
  `verifyToken` helper; do NOT touch session-cookie auth — that's T3.4") lets them start without
  re-deriving the plan. **A one-line title with an empty description is the single most common
  planning defect — do not ship it.** Set it with `--description` at creation, or edit the task's
  `description` field afterward; a task whose scope lives only in the planner's head is lost the
  moment the chat is gone.
- **At least one acceptance criterion.** Every task carries ≥1 checkable item in its
  `acceptance_criteria` list (set it with `set-criterion` on the task's `task.yaml`). A task with no
  verifiable criterion is not well-formed — don't leave it for "later". `validate.js` enforces the
  id/name and the criterion; the description is on you — it is no less required for being unenforced.

- **Say what depends on this task.** End the description with one line naming the tasks that
  consume this one's output — `Downstream: T2.3 (analysis pipeline), T2.5 (E2E).` — or, when
  nothing does, `Leaf: nothing consumes this.` It costs a line and it decides how hard the task is
  verified: a task whose output nothing consumes can only be wrong about itself, while one that
  defines a boundary, a type, a convention or a parse is wrong about **everything built on it** —
  and everything built on it will still pass its own tests. `mission-execution` reads this line to
  choose the gate (see its § *QA depth follows blast radius*). You are the only role that sees the
  whole mission at once, so you are the only one who can write it.
  Treat a task as downstream-critical when it defines a shared type, establishes a convention other
  tasks must independently re-apply, is the only thing touching git/the filesystem/the network, or
  produces output that gets persisted.

- **Write acceptance criteria as CONTRACTS: a stated input and its observable output.**
  QA verifies against the criteria and **nothing else** — not the description, not the plan, not
  the code, which it is forbidden to read. So anything a criterion leaves implicit is not verified
  by anyone. A criterion is not a topic to be checked; it is *given this input, that output*.

  ```
  weak      workspace manifests win over directories for module boundaries
  contract  given a repo whose only workspace signal is two go.mod files in different
            directories, the reported spine source is "manifests" and each of those two
            directories is a module
  ```

  The weak version is satisfiable by an implementation that handles one manifest type and silently
  ignores the rest — which is precisely how a real defect shipped: the criterion named no manifest
  type at all, the *description* listed five, and the two disagreed. Nothing enforced the
  description. **If an input class matters, name it in a criterion or accept that it is untested.**

  Three rules keep contracts from rotting:
  1. **State the input as a situation, not a call.** "A repo with two `go.mod` files" survives a
     refactor; `workspaceRoots()` returns `[...]` is stale the moment a function is renamed, and it
     also can't be checked by anyone who isn't reading the source.
  2. **State the output at the consumer-visible boundary** — the public API, the CLI's output, the
     file written. That is the level a consumer depends on and the only level QA can observe.
  3. **Give the negative and the degenerate case their own criteria.** "A single root-level marker
     yields `directories`" and "a marker inside `node_modules` is ignored" are contracts too, and
     they are where defects actually live. A criteria list with only happy paths is a list of
     things that were going to work anyway.

  This is also the cheapest test spec you will ever write: a contract-shaped criterion converts to
  a test almost mechanically, and the same sentence is what QA verifies black-box. When you cannot
  phrase a criterion this way, that is usually the requirement being unclear rather than the format
  being awkward — resolve it now, not after a task has been built against a guess.

**Id scheme.** Missions are `M<n>` numbered sequentially within their campaign (`M1`, `M2`, …); tasks
are `T<missionNumber>.<taskNumber>` within their mission (`T3.1`, `T3.2`, …). Read the existing board
(`list.js`) to find the next number. Missions title as `M<n> - <name>`, tasks as `T<m>.<n> - <name>`.
4. If the mission is backed by an implementation **plan** or a **design** doc (e.g. a `superpowers`
   plan under `docs/superpowers/plans/`, or a sibling `design.md`), record it as a document — see
   **Documents** below. The tasks come from the plan; without the plan linked, a resumed mission
   can't reconstruct why the tasks are what they are.
5. Consider whether the mission needs an **execution workflow** — see **Workflows** below. If its
   tasks have a real shape (a gate, a fan-out, work that can run concurrently), say so and point the
   user at the `workflow-designer` skill rather than designing it here.
6. Run `validate` and fix any well-formedness errors before you finish.

Principles: YAGNI — the fewest tasks that satisfy the mission's acceptance criteria. Every task is
verifiable: someone can tell when it's done. Stay within the mission's scope; if the mission itself
looks wrong, surface that to the user rather than silently expanding scope.

**End every mission with a verification task, owned by QA.** The last task on a mission board is a
task whose deliverable is *proof the mission works*, with `role: qa-engineer` — not another build
task, and not left implicit in the completion gate. It earns its place because it is the only task
whose acceptance criteria describe the mission's behaviour **as a whole**: the build tasks each verify
their own slice, and nothing else ever exercises them together. Give it real criteria like any other
task.

**Name it after the specific things that can break, not "write tests"** — name the regressions the
mission actually put at risk:

- `T6.6 - End-to-end: custom path, vendor-down fallback, and old-match regression`
- `T7.6 - End-to-end: local-team editing preserved, vendor rows read-only, no names in logs`

Each clause is a real hazard the mission introduced — a fallback that only matters when the vendor
is down, existing behaviour that must survive, a privacy boundary that must hold. A task called
"Tests" produces tests for what was easy to test; a task called "old-match regression, no names in
logs" produces the two tests that would actually have caught a shipped bug. Write this task **last,
once you know what the mission's build tasks put at risk** — the hazards are the output of planning
the rest, not something to guess up front.

This is not a substitute for the mission-completion gate. The task proves the mission's behaviour;
the gate independently re-verifies the criteria black-box and reviews the whole diff.

### Task chat — planner (tactical)

The task brief is `task.yaml`. Refine its detail and acceptance criteria with the same discipline:
small, verifiable, and scoped to the task. Use `set-criterion` to manage acceptance criteria and
run `validate` before you finish.

## Estimation (required on every mission and task)

**Every mission and every task carries an estimate, written at planning time.**
Effort is the sizing key and it cannot be recovered afterwards — nothing in a
transcript, a diff, or a PR reveals how long the work *would* have taken a
person. Miss it at planning and it is gone: the tokenomics collector reports it
as a gap, and cost-per-size stays uncalibrated.

### Where it goes

A `tokenomics` field — on `mission.yaml` for the mission, and on each
`tasks/<slug>/task.yaml` for its tasks. It is an **open map**, so it carries any
keys you need beyond the three below:

```yaml
tokenomics:
  effort_days: 3
  size_tshirt: M
  complexity_score: 18
```

Optional keys: `self_size` (your own label, kept to measure estimation drift),
`story_points`, `maturity` (`production` | `pilot` | `experimental`), and on a
mission `branches` when its branches don't follow the naming convention.

There is no dedicated script — add the `tokenomics` map by hand to the entity's
own `mission.yaml` / `task.yaml` (a plain key→value map). The app surfaces it
read-only on the mission/task detail panel, and the tokenomics collector reads
it for the cost report.

### 1. Estimate Effort first — this is the size

**`effort_days` = person-days for ONE person, with NO AI.** That definition is
what makes an `M` mean the same thing across roles, teams and repos. Do not
estimate the agent's wall-clock, and do not estimate cost.

| Band | Effort (1 person, no AI) | SDLC complexity score |
|---|---|---|
| XS | < ½ day | 6–9 |
| S | ~1 day | 10–14 |
| M | 2–3 days | 15–20 |
| L | 4–5 days | 21–26 |
| XL | > 1 sprint | 27–31 |

`size_tshirt` **is** the Effort band. The complexity score is the tie-breaker
when effort is genuinely uncertain: six dimensions — scope, risk, dependencies,
ambiguity, integration, validation — each 1–6, summed (6–36).

### 2. Audit it against the delivery signals

These do not outvote Effort; they catch a bad guess.

| Signal | XS | S | M | L | XL |
|---|---|---|---|---|---|
| Net LoC | ≤30 | ≤80 | ≤250 | ≤600 | 600+ |
| Files changed | 1–2 | 3–4 | 5–7 | 8–10 | 11–15+ |
| Component scope | 1 fn | 1 component | 2–3 comp | 3–4 comp | full-stack |
| Technical risk | exact pattern exists | established pattern | some new patterns | no precedent | novel |
| Affected layers | 1 | 2 | 2–3 | 3–4 incl. persistence | full stack |
| Subagent dispatches | ~3 | ~7 | ~10 | ~12 | ~16 |

Read the **dominant** band — the highest band reached by any *independent*
signal. **Do not average or majority-vote**: magnitude is what sizing means, so
a 600-LoC change is `L` even if four other signals say `S`. Collapse collinear
signals first (`net_loc` and `files_changed` count once).

### 3. Reconcile

- Signals within **±1 band** of Effort → keep the Effort size. The gap is noise.
- Signals **≥2 bands** away → **re-estimate before committing the plan.** Do not
  split the difference.
- Keeping a different local label? Put it in `self_size`. The gap between that
  and `size_tshirt` is the estimation-drift signal, and it is worth keeping.

**Cost is never a sizing input.** Sizing by measured cost would make
cost-per-size circular and destroy the only signal the measurement provides.

### Mission vs task

Size each **task** on its own work, and the **mission** on the whole thing — not
the sum of its tasks. A mission carries integration, review and the completion
gate that no single task owns, so mission effort normally exceeds the task
total. A mission whose effort exactly equals its tasks' sum is usually an
unestimated mission.

## Documents (specs, plans & designs)

A campaign or mission is often backed by a longer artifact — a **spec**, an implementation **plan**,
or a **design** doc — produced before or during planning (the `superpowers` workflow writes these to
`docs/superpowers/specs/` and `docs/superpowers/plans/`). These are the *why* behind the acceptance
criteria and tasks. **Link them to the entity** — an artifact that lives only on disk under
`docs/`, or only in a now-closed chat, is invisible to anyone who resumes the work from the board.
Linking them is what makes a campaign or mission recoverable.

Attach a document with **`add-doc.js`**, which appends a `{ label, target }` entry to the entity's
own `documents` list in its `campaign.yaml` / `mission.yaml` (documents attach to campaigns and
missions only — task/bug entities have none). It is idempotent on `target`. `target` is normally a
path **relative to the repo root** (or a URL):

```
add-doc.js <campaign-dir|campaign.yaml> "M1 spec" docs/superpowers/specs/2026-06-15-foo.md
add-doc.js <mission-dir|mission.yaml>   "M1 plan" docs/superpowers/plans/2026-06-15-foo.md
```

Two more notes:

- **Prefer `add-doc.js` over hand-editing** the `documents` list — it keeps each entry a
  well-formed `{ label, target }` and skips duplicates.
- **A doc specific to one entity** can also just live inside its folder (the `design.md` pattern — a
  doc next to `mission.yaml`); the app auto-surfaces folder files as documents. Use this for
  artifacts you author in place, and `add-doc.js` to link artifacts that live elsewhere (e.g. under
  `docs/superpowers/`).

## Status vocabulary

`draft` (not started) · `active`/`executing` (in progress) · `awaiting approval` (needs the
user) · `done` · `failed` · `cancelled`. By default a campaign's status rolls up from its missions:
`draft` while every mission is draft, `active` once any mission is executing/awaiting or partially
complete, `completed`/`failed`/`cancelled` when the missions agree. A campaign ALSO has a settable
explicit status that **overrides** the rollup (see below).

**Setting status on tasks and bugs.** Status is a **field in the child's own `task.yaml` /
`bug.yaml`** — there is no parent line to mark. Set it with `set-status.js <parent-dir> "<title>"
<state>` (it resolves the child by name within the parent folder and writes the child's own file),
e.g. `set-status.js <mission-dir> "T3.1 - Build the API" done`. It is idempotent: re-running
replaces the status, and the child's `role`/`severity`/other fields are preserved. Accepted states
map onto the vocabulary above: `active` (or `in progress`) → `executing`, `awaiting approval` →
awaiting-approval, plus `draft`/`done`/`failed`/`cancelled`.

**When to transition (do this as you work, not at the end).** Updating status is part of doing the
work, not an afterthought — a board full of `draft` items the moment work has actually started or
finished is wrong and misleads everyone reading it. Mark a task or bug `active` the moment you pick
it up, and `done` the moment all of its acceptance criteria are checked and verified — don't leave
finished work sitting in `draft`. Use `failed`/`cancelled` if the work cannot or should not complete.

**Setting a campaign's own status.** A campaign's status is the `status` field in its own
`campaign.yaml` (default `draft`). Setting it to any non-`draft` value
(`done`/`cancelled`/`failed`/`executing`/`awaiting approval`) **overrides** the mission rollup; leave
it `draft` to keep the derived rollup. Set it with
`set-status.js <campaign-dir> "<Campaign name>" <state>` (pass the campaign's own `name` as the
title), which writes the `status` field on `campaign.yaml`.

**Setting status on a mission — two layers, don't conflate them.** A mission's status lives at two
layers, and this is a common trip-up:

- **The app's displayed status** is driven by the mission's run lifecycle (Start/Cancel) and its task
  rollup. The `status` field set-status.js writes on `mission.yaml` does **not** override that — in
  that sense it is inert *to the app* (unlike a task/bug status field, which *is* its entity's
  status).
- **The completion gate** is triggered by the *act* of flipping the mission `done` with
  `set-status.js <campaign-dir> "<M<n> - name>" done`: the `.octobots/hooks/mission-gate.mjs`
  PostToolUse hook watches that invocation and launches the **mission-completion-gate** skill. So the
  command is emphatically **not** a no-op on a mission — it is the intended trigger for the gate.

**How to act:** to complete a mission, run `set-status.js … done` on it. That fires the gate, which
must pass green before the mission is truly done — fix and re-verify if it surfaces blocking findings
(you may also run `mission-completion-gate` by hand first and flip `done` once it is green). Do **not**
skip the mission flip thinking it is "ignored": the field doesn't drive the app's status, but the
act of setting it `done` is exactly what launches the gate. So `set-status.js` applies to missions
too — for a task or bug it *sets* the entity's status; for a mission it *triggers that mission's
completion gate*. See **mission-completion-gate**.

## Workflows (how the work runs — see the **workflow-designer** skill)

A **workflow** is the plan of execution that sits beside the work: the order of the steps and the
agents to call. A **campaign** workflow orchestrates its missions; a **mission** workflow
orchestrates its tasks, and a mission has at most one.

```
.octobots/campaigns/<campaign>/workflows/<slug>/workflow.js     # the script (meta = name/description/phases + body)
.octobots/campaigns/<campaign>/workflows/<slug>/runs.jsonl      # append-only run log (created on first run)
```

**That is not your job here.** Designing or editing a workflow — choosing phases, agents and what
runs in parallel, and authoring the script — belongs to the **workflow-designer** skill. Running one
belongs to **mission-execution**. Your job is the board: missions, tasks and acceptance criteria.

When you finish decomposing a mission and its shape is worth recording — a review gate, a fan-out,
work that can run concurrently — **say so and point the user at `workflow-designer`**. Don't
hand-edit `workflow.js`: its `export const meta` must stay a pure object literal or the app can no
longer draw the workflow, and `set-step.js` is what guarantees that.

## Naming the agent on a task — the `role` field

A task can name the agent that should pick it up, with a `role` field in its own `task.yaml`:

```yaml
name: T1.1 - Add JWT validation to /login
role: implementer
status: draft
```

`role` is an **agent name** — the same vocabulary a workflow step's `agent` field uses, and
normally a `.claude/agents/<name>` directory. Run `ls .claude/agents` to see what the repo has.

Write it at creation with `add-task.js <mission-dir> "<title>" --role <name>`; the role is stored as
a field, so the task name stays `T1.1 - Add JWT validation to /login`. `set-status.js` and other
edits preserve it, so a task keeps its agent as it moves through the board.

This works **with or without a workflow**, and the two answer different questions:

- `role` says **who** should do this one task.
- A workflow says **in what order** the steps run and **which agent** each one calls.

Use `role` when the assignment is per-task and situational; use a workflow when the whole
sequence is worth writing down and running. A mission can sensibly have both — the workflow drives
the run, and `role` records who owns an individual task.

> The `role` field is read by agents from the task's YAML; Octoshell does not currently surface it
> in the task panel.

## External systems (Epics, Stories, Tasks)

Octobots work often mirrors an external planning system — Jira, GitHub Projects/Issues, Azure DevOps,
onetest-tms, etc. The hierarchy maps one-to-one:

| Octobots  | External                  |
|-----------|---------------------------|
| campaign  | Epic (or Initiative)      |
| mission   | Story (or Feature)        |
| task      | Task (or Sub-task)        |
| bug       | Bug / Defect              |

Work flows in **either direction**, and the Octobots board is always the source of truth for execution
(the external item is for planning visibility and traceability):

- **Originated externally** — when the user points you at an Epic/Story/Task/ticket ("plan epic ABC-123",
  "sync this story", "import these issues"), create the matching Octobots entity on the board (campaign /
  mission / task via the scripts) so the work becomes executable on the board. Carry over the title,
  description, and acceptance criteria, and keep the external id in the entity's `description` field
  for traceability (e.g. `Source: JIRA ABC-123`).
- **Originated in Octobots** — after you create a campaign/mission/task (or bug), **offer to mirror it**
  out to the external system if one is configured (an MCP server such as `github` or `onetest-tms`).
  Don't create the external item silently, don't let edits go *only* to the external system, and don't
  treat an external ticket as a replacement for the board. Keep ids cross-referenced both ways.

Bugs follow this same rule — see below.

## Bugs

A **bug** records faulty behaviour found while implementing. Bugs are first-class work items that
sit on a **campaign** (cross-cutting) or a **mission** (sibling to its tasks), each with its own
`bug.yaml` brief (`severity`, `status`, `description`, `steps_to_reproduce`, `expected`, `actual`,
`rca`, `environment`) and its own folder under `<parent>/bugs/<slug>`. A bug is executable like a
task, bound to its parent.

When asked to create, file, log, or report a bug or defect in an Octobots repo, record it **here first**
as an Octobots bug — even when the repo also has a GitHub issues or onetest-tms integration. A GitHub
issue or external tracker ticket is **not** a substitute: it is not executable and not on the board.
After creating the Octobots bug, **offer to mirror it** to the external tracker (e.g. open
a matching GitHub issue / TMS defect) if one is configured — but don't file the bug *only* there, and
don't switch to the external tracker unless the user explicitly asks for that instead.

To log a bug, run `add-bug.js <campaign-dir|mission-dir> "<title>" [--severity <level>]` — it creates
the `bugs/<slug>/bug.yaml` folder (the parent is not touched; bugs are folder-derived). Fill in the
details (steps, expected/actual, RCA) by editing that `bug.yaml`. Severity is one of `blocker`,
`critical`, `major` (default), `minor`, `trivial`, and is stored as the `severity` field on the
bug's own YAML.

To **delete** a bug, use `delete-bug.js` (which trashes its `bugs/<slug>/` folder — the `.octobots`
tree is the source of truth, so removing the folder is what removes the bug). Likewise
`delete-task.js` for a task. Deleting a **mission** or **campaign** is done from the Octoshell UI (it
also removes the entity's chat history, which lives outside the board).

## Scripts (prefer these over hand-editing — they save tokens and keep the YAML well-formed)

Run from the repo root:

- `node .claude/skills/mission-planner/scripts/list.js` — print the campaign → mission → task tree.
- `node .claude/skills/mission-planner/scripts/show.js <entity-dir|entity.yaml>` — print an entity or a compact digest.
- `node .claude/skills/mission-planner/scripts/add-campaign.js "<name>" [--description <text>] [--target <text>] [--root <dir>]` — create a campaign folder + `campaign.yaml`. `--root` defaults to `.octobots`.
- `node .claude/skills/mission-planner/scripts/add-mission.js <campaign-dir|campaign.yaml> "<title>" [--description <text>]` — create a mission folder + `mission.yaml` under a campaign (the campaign is not touched — missions are folder-derived). It starts with no acceptance criteria — add them with set-criterion.js.
- `node .claude/skills/mission-planner/scripts/add-task.js <mission-dir|mission.yaml> "<title>" [--role <agent>]` — create a task folder + `task.yaml` under a mission (the mission is not touched). `--role` writes the `role` field naming the agent that should take it.
- `node .claude/skills/mission-planner/scripts/add-bug.js <campaign-dir|mission-dir|entity.yaml> "<title>" [--severity <level>]` — create a bug folder + `bug.yaml` under a campaign or mission (the parent is not touched).
- `node .claude/skills/mission-planner/scripts/add-doc.js <campaign-dir|mission-dir|entity.yaml> "<label>" <target>` — attach a document: append a `{ label, target }` entry to the entity's own `documents` list (idempotent on target; campaigns and missions only).
- `node .claude/skills/mission-planner/scripts/delete-bug.js <campaign-dir|mission-dir|entity.yaml> "<title>"` — delete a bug: trashes its `bugs/<slug>/` folder.
- `node .claude/skills/mission-planner/scripts/delete-task.js <mission-dir|mission.yaml> "<name>"` — delete a task: trashes its `tasks/<slug>/` folder.
- `node .claude/skills/mission-planner/scripts/set-criterion.js <entity-dir|entity.yaml> add "<text>" | check <n> | uncheck <n>` — manage the entity's own `acceptance_criteria`.
- `node .claude/skills/mission-planner/scripts/set-status.js <parent-dir|entity.yaml> "<entity title>" <state>` — set the `status` field in the named child's own YAML (or the parent's, for a campaign/mission self-status); idempotent, preserves the entity's other fields. On a **mission** the field doesn't drive the app's status, but setting it `done` fires the mission-completion-gate hook — see *Setting status on a mission* above.
- `node .claude/skills/mission-planner/scripts/migrate.js [--root <dir>]` — one-time, idempotent md→yaml conversion for a board still on the legacy Markdown files (the app runs the same sweep on activation; use this for a CLI-first board opened before the app). It parses each `<kind>.md`, folds the old parent `[status:]`/`[role:]`/`[severity:]` markers and `## Tokenomics` into the child's YAML, writes `<kind>.yaml`, and trashes the `.md`. A folder already on YAML is skipped.
These three are the **workflow-designer** skill's tools — they live here because every board writer
shares one `scripts/` directory, but that skill owns the doctrine for using them:

- `node .claude/skills/mission-planner/scripts/add-workflow.js --campaign <slug> [--mission <slug>] --name "<name>" [--description "<text>"]` — scaffold a workflow folder with a runnable `workflow.js` (name/description/phases in its `meta`). Refuses a second workflow on a mission.
- `node .claude/skills/mission-planner/scripts/set-step.js --workflow <workflow-dir> --phase "<title>" --id <stepId> --agent <name> --label "<text>" [--parallel <group>] [--depends-on <id,id>] [--backend <name>]` — upsert a step in the script's `meta`, rewriting only that literal and leaving the body untouched.
- `node .claude/skills/mission-planner/scripts/add-run.js --workflow <workflow-dir> --status <state> --summary "<text>" [--at YYYY-MM-DD]` — append a run entry (one JSON line) to the workflow's `runs.jsonl`.
- `node .claude/skills/mission-planner/scripts/validate.js <entity-dir|entity.yaml>` — check an entity is well-formed AND meets the contract: a descriptive (non-placeholder) name, for missions/tasks at least one acceptance criterion, and no acceptance criteria stranded as `- [ ]` prose inside `notes`. Given a `workflow.js` (or a workflow folder) it checks the workflow's script instead (meta present and literal, name matches the folder, phases and steps well-formed); given a campaign/mission it also checks every workflow beneath it. Run it after editing and fix every problem.
