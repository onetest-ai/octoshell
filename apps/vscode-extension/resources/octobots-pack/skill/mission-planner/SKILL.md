# Octobots Workflow

Octobots organizes work as **campaigns → missions → tasks**. Each lives as a markdown
"board" file under `.octobots/`, and **the `.octobots/` tree is the source of truth** —
editing those files (via these scripts) is how you drive Octobots; the app reads them
live. You do not call an API. Each entity is a **folder** (`campaign.md` / `mission.md` /
`task.md` / `bug.md`) and is identified by its **folder path** — no id marker is written into
the file. The scripts create those folders. A bare `## Tasks` / `## Bugs` board line is
only a status/role projection of a folder-backed entity — it does **not** create one, so always
use `add-task.js` / `add-bug.js` (which write the folder) rather than hand-adding a line.

## Layout

```
.octobots/campaigns/<campaign-slug>/campaign.md
.octobots/campaigns/<campaign-slug>/missions/<mission-slug>/mission.md
.octobots/campaigns/<campaign-slug>/missions/<mission-slug>/tasks/<task-slug>/task.md
```

Your working directory is the repo root, so these are real relative paths.

## Board anatomy

Every board has a **managed header** the app owns, then an **agent-owned** section. The
boundary is an HTML comment containing `Auto-generated by Octobots`. Example `mission.md`:

```markdown
# <Mission title>

## Description
<one-paragraph description>

## Acceptance Criteria
- [ ] a concrete, checkable criterion
- [x] a criterion already met

## Sessions
_(no execution sessions yet)_

<!-- Auto-generated by Octobots ... -->
## Tasks
1. **Phase title**
   - [ ] sub-step
   - [ ] sub-step
```

Rules:
- **Above the comment** (`## Description`, `## Acceptance Criteria`, `## Sessions`): the app
  generates these from its database, but your edits to **Description** and **Acceptance
  Criteria** sync back. Acceptance criteria are a checklist — one `- [ ]` (or `- [x]`) per line.
- **Below the comment**: yours. In `campaign.md` it is `## Missions`; in `mission.md`/`task.md`
  it is `## Tasks`. Never delete or move the `Auto-generated by Octobots` comment.

## Planning by scope

Which board you plan against — and how — depends on the chat scope. The host puts you in one
of these modes via a thin planning agent (`octobots-orchestrator` for campaigns,
`octobots-planner` for missions and tasks); follow the matching doctrine below.

### Campaign chat — orchestrator (strategic)

You turn an intent into a **campaign** and its **missions**. Think top-down: outcome → missions
→ acceptance criteria. You do NOT break missions into individual tasks — that is the planner's job.

1. Clarify the campaign outcome with the user — one focused question at a time when something is
   genuinely ambiguous; otherwise propose and proceed.
2. Decompose the outcome into a small set of missions, each independently shippable and each with
   explicit acceptance criteria.
3. Propose missions by writing them into `campaign.md` under a `## Missions` heading, one per line
   as `- M<n> - <Mission name> — <one-line description>` — a sequential id (`M1`, `M2`, …), a
   descriptive name, then an em-dash and the one-line description (the ` - ` after the id stays in
   the title; the ` — ` em-dash starts the description). The user reviews and creates them.
4. If the campaign is backed by a design **spec** (e.g. a `superpowers` spec under
   `docs/superpowers/specs/`), record it as a document — see **Documents** below. Don't leave the
   spec linked only in chat; an unlinked spec is lost work when the chat is gone.
5. Run `validate` and fix any well-formedness errors before you finish.

Principles: YAGNI — propose the fewest missions that achieve the outcome. Every mission has at
least one acceptance criterion. Keep missions independent; if two must happen in a fixed order,
say so explicitly. Stay at strategic altitude — leave task decomposition to the planner.

### Mission chat — planner (tactical)

You break a **mission** into executable **tasks**. Work within the mission's scope; you do NOT
create or re-scope campaigns (that is the orchestrator's job).

1. Read the mission board to understand its scope and acceptance criteria.
2. Decompose into tasks that are each small, independently verifiable, and ordered only where a
   real dependency exists.
3. Write tasks into `mission.md` under `## Tasks` with `add-task`, and attach acceptance criteria
   with `set-criterion`. Each top-level item (a numbered phase or a top-level `-` bullet) becomes
   one task; nested `- [ ]` lines under it become that task's description.

**Task contract (required — `validate.js` enforces it):**
- **Id + descriptive name.** Title every task as `<id> - <descriptive name>`: a short hierarchical
  id, then a real name — e.g. `T3.1 - Add JWT validation to the /login endpoint`. The id is a stable,
  human-readable handle (so a person or the model can say "do T3.1"); the name says what the task
  accomplishes. A **bare id with no name** (`T1`, `T5.5`) is rejected, and so is an undescriptive
  name. Use a literal ` - ` (space-hyphen-space) between id and name — the parser keeps it as one
  title (only an em-dash ` — ` or a colon starts an inline description).
- **At least one acceptance criterion.** Every task carries ≥1 checkable `- [ ]` item under its
  `## Acceptance Criteria` (set it with `set-criterion` on the task's `task.md`). A task with no
  verifiable criterion is not well-formed — don't leave it for "later".

**Id scheme.** Missions are `M<n>` numbered sequentially within their campaign (`M1`, `M2`, …); tasks
are `T<missionNumber>.<taskNumber>` within their mission (`T3.1`, `T3.2`, …). Read the existing board
(`list.js`) to find the next number. Missions title as `M<n> - <name>`, tasks as `T<m>.<n> - <name>`.
4. If the mission is backed by an implementation **plan** or a **design** doc (e.g. a `superpowers`
   plan under `docs/superpowers/plans/`, or a sibling `design.md`), record it as a document — see
   **Documents** below. The tasks come from the plan; without the plan linked, a resumed mission
   can't reconstruct why the tasks are what they are.
5. Run `validate` and fix any well-formedness errors before you finish.

Principles: YAGNI — the fewest tasks that satisfy the mission's acceptance criteria. Every task is
verifiable: someone can tell when it's done. Stay within the mission's scope; if the mission itself
looks wrong, surface that to the user rather than silently expanding scope.

### Task chat — planner (tactical)

The task brief is `task.md`. Refine its detail and acceptance criteria with the same discipline:
small, verifiable, and scoped to the task. Use `set-criterion` to manage acceptance criteria and
run `validate` before you finish.

## Estimation (required on every mission and task)

**Every mission and every task carries an estimate, written at planning time.**
Effort is the sizing key and it cannot be recovered afterwards — nothing in a
transcript, a diff, or a PR reveals how long the work *would* have taken a
person. Miss it at planning and it is gone: the tokenomics collector reports it
as a gap, and cost-per-size stays uncalibrated.

### Where it goes

A `## Tokenomics` block — on `mission.md` for the mission, and on each
`tasks/<slug>/task.md` for its tasks (the planner owns any section appended
below the managed-block marker):

```markdown
## Tokenomics
effort_days: 3
size_tshirt: M
complexity_score: 18
```

Optional: `self_size` (your own label, kept to measure estimation drift),
`story_points`, `maturity` (`production` | `pilot` | `experimental`), and on a
mission `branches:` when its branches don't follow the naming convention.

### 1. Estimate Effort first — this is the size

**`effort_days` = person-days for ONE person, with NO AI.** That definition is
what makes an `M` mean the same thing across roles, teams and repos. Do not
estimate the agent's wall-clock, and do not estimate cost.

| Band | Effort (1 person, no AI) | SDLC complexity score |
|---|---|---|
| XS | < ½ day | 6–9 |
| S | ~1 day | 10–14 |
| M | 2–3 days | 15–20 |
| L | 4–5 days | 21–26 |
| XL | > 1 sprint | 27–31 |

`size_tshirt` **is** the Effort band. The complexity score is the tie-breaker
when effort is genuinely uncertain: six dimensions — scope, risk, dependencies,
ambiguity, integration, validation — each 1–6, summed (6–36).

### 2. Audit it against the delivery signals

These do not outvote Effort; they catch a bad guess.

| Signal | XS | S | M | L | XL |
|---|---|---|---|---|---|
| Net LoC | ≤30 | ≤80 | ≤250 | ≤600 | 600+ |
| Files changed | 1–2 | 3–4 | 5–7 | 8–10 | 11–15+ |
| Component scope | 1 fn | 1 component | 2–3 comp | 3–4 comp | full-stack |
| Technical risk | exact pattern exists | established pattern | some new patterns | no precedent | novel |
| Affected layers | 1 | 2 | 2–3 | 3–4 incl. persistence | full stack |
| Subagent dispatches | ~3 | ~7 | ~10 | ~12 | ~16 |

Read the **dominant** band — the highest band reached by any *independent*
signal. **Do not average or majority-vote**: magnitude is what sizing means, so
a 600-LoC change is `L` even if four other signals say `S`. Collapse collinear
signals first (`net_loc` and `files_changed` count once).

### 3. Reconcile

- Signals within **±1 band** of Effort → keep the Effort size. The gap is noise.
- Signals **≥2 bands** away → **re-estimate before committing the plan.** Do not
  split the difference.
- Keeping a different local label? Put it in `self_size`. The gap between that
  and `size_tshirt` is the estimation-drift signal, and it is worth keeping.

**Cost is never a sizing input.** Sizing by measured cost would make
cost-per-size circular and destroy the only signal the measurement provides.

### Mission vs task

Size each **task** on its own work, and the **mission** on the whole thing — not
the sum of its tasks. A mission carries integration, review and the completion
gate that no single task owns, so mission effort normally exceeds the task
total. A mission whose effort exactly equals its tasks' sum is usually an
unestimated mission.

## Documents (specs, plans & designs)

A campaign or mission is often backed by a longer artifact — a **spec**, an implementation **plan**,
or a **design** doc — produced before or during planning (the `superpowers` workflow writes these to
`docs/superpowers/specs/` and `docs/superpowers/plans/`). These are the *why* behind the acceptance
criteria and tasks. **Link them to the entity** — an artifact that lives only on disk under
`docs/`, or only in a now-closed chat, is invisible to anyone who resumes the work from the board.
Linking them is what makes a campaign or mission recoverable.

Attach a document with **`add-doc.js`**, which adds a `- [label](target)` link to the entity's
`## Documents` section (campaign and mission boards both have one). These link lines **round-trip**:
the app parses them back into the entity's documents, so the attachment survives every resync and is
greppable from the board file. `target` is normally a path **relative to the repo root** (or a URL):

```
add-doc.js campaign.md "M1 spec" docs/superpowers/specs/2026-06-15-foo.md
add-doc.js mission.md  "M1 plan" docs/superpowers/plans/2026-06-15-foo.md
```

Two more notes:

- **Don't hand-edit the rest of the managed `## Documents` block** — plain `- name` lines (files in
  the entity folder) and `- label (target)` lines (attached files) are app-owned and regenerated.
  Only the `- [label](target)` link lines are yours; `add-doc.js` writes them well-formed.
- **A doc specific to one entity** can also just live inside its folder (the `design.md` pattern — a
  doc next to `mission.md`); the app auto-surfaces folder files under `## Documents`. Use this for
  artifacts you author in place, and `add-doc.js` to link artifacts that live elsewhere (e.g. under
  `docs/superpowers/`).

## Status vocabulary

`draft` (not started) · `active`/`executing` (in progress) · `awaiting approval` (needs the
user) · `done` · `failed` · `cancelled`. By default a campaign's status rolls up from its missions:
`draft` while every mission is draft, `active` once any mission is executing/awaiting or partially
complete, `completed`/`failed`/`cancelled` when the missions agree. A campaign ALSO has a settable
explicit status that **overrides** the rollup (see below).

**Setting status on tasks and bugs.** A task or bug line in a parent's `## Tasks` / `## Bugs`
section can carry a `[status:<state>]` marker (parsed exactly like `[severity:]`/`[role:]` — stripped
from the title, mapped to the entity's status on the next sync). Set it with `set-status.js` rather
than hand-editing, e.g. `set-status.js mission.md "Build the API" done`. The marker is idempotent: re-
running replaces the old status, never duplicates it, and any `[severity:]`/`[role:]` marker on the
line is preserved. Accepted states map onto the vocabulary above: `active` (or `in progress`) →
`executing`, `awaiting approval` → awaiting-approval, plus `draft`/`done`/`failed`/`cancelled`.

**When to transition (do this as you work, not at the end).** Updating status is part of doing the
work, not an afterthought — a board full of `draft` items the moment work has actually started or
finished is wrong and misleads everyone reading it. Mark a task or bug `active` the moment you pick
it up, and `done` the moment all of its acceptance criteria are checked and verified — don't leave
finished work sitting in `draft`. Use `failed`/`cancelled` if the work cannot or should not complete.

**Setting a campaign's own status.** A campaign has no parent board line, so its status lives in
its own `## Status` section in `campaign.md` (default `draft`). Setting it to any non-`draft` value
(`done`/`cancelled`/`failed`/`executing`/`awaiting approval`) **overrides** the mission rollup; leave
it `draft` to keep the derived rollup. Set it by editing the `## Status` body, or with
`set-status.js campaign.md "<Campaign name>" <state>` (pass the campaign's own name — its `# heading` —
as the title), which writes/replaces that section. **Missions** are still driven by the app's run
lifecycle (Start/Cancel) rather than a board marker; a `[status:]` marker on a mission line is ignored.

## External systems (Epics, Stories, Tasks)

Octobots work often mirrors an external planning system — Jira, GitHub Projects/Issues, Azure DevOps,
onetest-tms, etc. The hierarchy maps one-to-one:

| Octobots  | External                  |
|-----------|---------------------------|
| campaign  | Epic (or Initiative)      |
| mission   | Story (or Feature)        |
| task      | Task (or Sub-task)        |
| bug       | Bug / Defect              |

Work flows in **either direction**, and the Octobots board is always the source of truth for execution
(the external item is for planning visibility and traceability):

- **Originated externally** — when the user points you at an Epic/Story/Task/ticket ("plan epic ABC-123",
  "sync this story", "import these issues"), create the matching Octobots entity on the board (campaign /
  mission / task via the scripts) so the work becomes executable on the board. Carry over the title,
  description, and acceptance criteria, and keep the external id in the entity's `## Description` for
  traceability (e.g. `Source: JIRA ABC-123`).
- **Originated in Octobots** — after you create a campaign/mission/task (or bug), **offer to mirror it**
  out to the external system if one is configured (an MCP server such as `github` or `onetest-tms`).
  Don't create the external item silently, don't let edits go *only* to the external system, and don't
  treat an external ticket as a replacement for the board. Keep ids cross-referenced both ways.

Bugs follow this same rule — see below.

## Bugs

A **bug** records faulty behaviour found while implementing. Bugs are first-class work items that
sit on a **campaign** (cross-cutting) or a **mission** (sibling to its tasks), each with its own
`bug.md` brief (Severity, Description, Steps to Reproduce, Expected, Actual, RCA, Environment) and its
own folder under `<parent>/bugs/<slug>`. A bug is executable like a task, bound to its parent.

When asked to create, file, log, or report a bug or defect in an Octobots repo, record it **here first**
as an Octobots bug — even when the repo also has a GitHub issues or onetest-tms integration. A GitHub
issue or external tracker ticket is **not** a substitute: it is not executable and not on the board.
After creating the Octobots bug, **offer to mirror it** to the external tracker (e.g. open
a matching GitHub issue / TMS defect) if one is configured — but don't file the bug *only* there, and
don't switch to the external tracker unless the user explicitly asks for that instead.

To log a bug, append it to the parent's `## Bugs` board with `add-bug.js` (don't hand-edit — the script
keeps the file well-formed). Octoshell discovers the line and creates the bug entity + its `bug.md`;
fill in the details (steps, expected/actual, RCA) in that `bug.md`. Severity is one of `blocker`,
`critical`, `major` (default), `minor`, `trivial` and rides a `[severity:<level>]` marker on the board
line.

To **delete** a bug, use `delete-bug.js` (don't just remove the board line — the `.octobots` tree is the
source of truth and a bug whose `bugs/<slug>/` folder still exists is kept, so the script removes BOTH
the `## Bugs` line and the folder). Likewise `delete-task.js` for a task. Deleting a **mission** or
**campaign** is done from the Octoshell UI (it also removes the entity's chat history, which lives
outside the board).
