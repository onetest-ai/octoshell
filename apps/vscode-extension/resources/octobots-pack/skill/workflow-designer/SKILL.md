# workflow-designer

You turn a **planned** board into a **plan of execution**: which agents run, in what order, and what
runs in parallel.

```
mission-planner     what work exists      (missions, tasks, acceptance criteria)
      ↓
workflow-designer   how it will run       (phases, agents, parallelism)   ← you are here
      ↓
mission-execution   run it, log the run
```

You do **not** decompose work into missions and tasks — that is `mission-planner`. You do **not**
run the workflow — that is `mission-execution`, which hands `workflow.js` to Claude Code's
`Workflow` tool.

## When a workflow is worth writing

A workflow is a real artifact with a real maintenance cost. Write one when the *sequence* is worth
recording, not merely because a mission exists: the tasks have a shape (a review gate, a fan-out, a
build-then-verify order) a person would otherwise re-derive each run; several **read-only** steps can
run concurrently and you want that stated rather than discovered; the same sequence runs more than
once; different steps want different agents.

**Don't** write one for a handful of independent tasks with no ordering — `mission-execution`
already composes a mission loop for that — and don't invent structure to look thorough. If you
decide against one, **say so and why**; silence reads as an oversight. If you cannot tell whether the
tasks are genuinely independent, ask **`knowledge-explorer`** first: `conflicts <mission>` answers
exactly that, and parallelising tasks that co-change is how a workflow produces a merge conflict on
every run.

## The two levels

A **campaign** workflow orchestrates that campaign's **missions**; a **mission** workflow
orchestrates that mission's **tasks**. Design at the level you were asked about — a campaign
workflow whose steps are individual tasks is at the wrong altitude, and so is the reverse. Either
level may hold several; nothing limits the count.

## The three loops

A mission does not have one execution loop. It has three, taking different inputs, applying
different gates, running at different times:

| Slug | Iterates over | Runs |
|---|---|---|
| `implementation` | the mission's **tasks** | once, while the mission is being built |
| `testing` | **test cases** / acceptance criteria | after implementation, and again after every later mission |
| `fixing` | **open bugs** | whenever bugs accumulate |

Use those slugs — a run is selected by name, so the name has to say which loop it is.

**Do not fold them into one script with a `mode` argument.** The diagram is generated from the whole
script body, so one script covering all three draws all three, and every run advertises phases it
never enters. Three scripts, three honest diagrams.

**Write only the loops the mission actually needs.** Most missions start with `implementation`
alone; add `testing` when there are criteria worth re-running and `fixing` when bugs have actually
accumulated. Three near-empty workflows is the same YAGNI failure as a workflow for three
independent tasks. At campaign level a bug-fix loop belongs on the **mission** that owns the bugs.

## Resolve the agents first — never invent them

A step's `agentType` names a real agent. **Before designing anything, find out what exists:**

```bash
ls .claude/agents          # the repo's agents, one directory per agent
```

**The Octobots pack installs no agents at all** — it ships skills and a session hook. Every name you
can use comes from the repo itself, and many repos have none. So **use names that exist**: a step
naming an agent the repo lacks fails at run time and still shows as valid, because `validate.js`
checks that a step *says* which agent it wants, not that it is installed. If there is no suitable
agent, do not substitute a plausible-sounding role — `implementer`, `tester`, `reviewer` are
*examples in documentation*, not agents. Ask once, with the list you found: install one, name an
existing one, or accept the default subagent. Prefer fewer real agents over a rich cast of imaginary
ones; every agent name in the examples below is a placeholder for this reason.

State which agents you found and which you used. That sentence is what makes the workflow auditable.

## Designing the run

1. **Read the board first.** `list.js` for the tree, the mission's `mission.yaml` for its tasks and
   criteria. A workflow that ignores them is fiction.
2. **Group tasks into phases** a person would name — *Plan*, *Build*, *Verify*, *Review*, *Ship*.
   Keep it to a handful; a phase per task is not a design.
3. **Almost nothing runs concurrently.** Calls inside one `parallel([…])` run together, and **only
   read-only steps belong there** (reviewers on a finished diff, parallel analyses). Anything that
   writes files is **sequenced**, even when two tasks look independent: every mission runs in the
   **one root working tree** on one branch, so concurrent writers corrupt it. There is no worktree
   escape hatch (see `mission-execution` § *Non-negotiable principles*) — the answer to "these could
   run in parallel" is to order them. If you find yourself wrapping a build in `parallel()`, stop.
4. **Put the gates in.** If a stage must not proceed on red, make it its own phase so the shape is
   visible.
5. **Design the not-green path — a workflow is not a sunny-day DAG.** A real run surfaces review
   findings and QA bugs; a plan that only draws Build → Review → Verify → Gate assumes each passes
   first try, and that optimism makes a run read as done when it isn't. Remediation lives in
   **control flow**: after blocking findings, loop *dev addresses each finding + adds the regression
   test → re-review*, bounded (≤2 rounds); after a QA failure, loop *dev fixes → re-verify*, bounded;
   still red after the bound, **`return { blocked: … }`** instead of walking on to the gate. See
   `mission-execution` § *The mission loop* for the bounds.

   > **Better still, put the remediation inside the reviewing agent** — it fixes each blocking
   > finding itself, adds the regression test, re-runs green, and returns `final_state_green`
   > alongside the findings. Fewer agents, finding and fix in one head, no hand-off loss. It changes
   > the gate condition: branch on **`final_state_green`**, never on "were there findings", because
   > with in-agent remediation a non-empty list is the normal shape of a *successful* review. Either
   > way, **an unbounded retry is not an option**.
6. **End a mission workflow at the gate, not at the last merge.** Merged tasks are not a green
   mission: per-task gates check per-task criteria, and nothing has yet verified the *mission's*
   criteria or exercised the tasks together. Finish with a phase that flips the mission `done` and
   runs the **`mission-completion-gate`**. Static gates between tasks, **one dynamic gate per
   mission**; a workflow whose last phase is "merge" is unfinished.

## The file format

```
.octobots/campaigns/<campaign>/workflows/<slug>/workflow.js    # the executable script (meta + body)
.octobots/campaigns/<campaign>/workflows/<slug>/runs.jsonl     # append-only run log (created on first run)
.octobots/campaigns/<campaign>/missions/<mission>/workflows/<slug>/…
```

`workflow.js` is a **Claude Code dynamic-workflow script**. Its `export const meta` block is what the
board draws — and it is **generated from the body below it**, never hand-written. You write the
program; `sync-meta.js` writes the picture. Three fields are yours and survive every regenerate:
`name`, `description`, and a phase's optional `detail` — the caption Claude Code's own Workflow
runtime reads. Everything else in `meta` is derived, so editing it by hand only lasts until the next
`sync-meta.js`.

That means the annotations on your calls are load-bearing. `{ phase }` places a step in a band,
`{ label }` captions it, and **`{ agentType }` is what both dispatches the agent and names it on the
diagram** — one field, so the board cannot advertise an agent that never ran.

```js
phase('Build')
const built = await agent(buildPrompt(t), { phase: 'Build', label: 'build ' + t.id, agentType: 'ios-dev' })
```

The extractor reads control flow, so the picture matches the run: calls inside `parallel([…])` draw
as one fan-out, calls inside a loop or a `pipeline()` draw once with a `×N` badge, and everything
else chains in the order you wrote it. `parallel(tasks.map(…))` gets the badge too — its members are
computed, so one call site stands for N concurrent runs; only a literal array of thunks draws its
members as separate nodes. **An `agent()` call with no `agentType` is a validate failure**, not a
node the diagram labels — it would run as the default subagent with no persona, tools or
instructions, so it never reaches the picture. A **computed** one (`agentType: task.role`) is fine
and dispatches for real; the extractor simply cannot read the name, so that node draws with no agent
shown. Give every member of one `parallel([…])` the **same `{ phase }`**: each call's
phase is resolved on its own, so mixed values split one fan-out across two bands.

A step is not necessarily an agent: `kind` is `agent` by default, `workflow` for a `workflow()` call,
and `command` when you mark one. Everything else on a step — `id`, `repeat`, `parallel`, `dependsOn`
— is derived from the code's shape, and `{ backend }` (`claude` | `copilot` | `codex`) carries
through when a step must run on a specific CLI. Write `label`s as actions (`build T2`,
`review the diff`), not restated agent names; ids are generated, so you never write one.

### The body is the design

```js
phase('Plan')
const tasks = await agent(planPrompt(ARGS), { phase: 'Plan', label: 'decompose the mission', agentType: 'tech-lead', schema: TASKS })

for (const t of tasks) {                       // writers share one tree — strictly sequential
  phase('Build')
  let build = await agent(buildPrompt(t), { phase: 'Build', label: 'build ' + t.id, agentType: 'js-dev', schema: IMPL })

  // Declared INSIDE the loop on purpose — see the attribution warning below.
  const reviewRound = (b) => parallel([
    () => agent(reviewPrompt(t, b, 'correctness'), { phase: 'Review', label: 'review correctness', agentType: 'tech-lead', schema: REVIEW }),
    () => agent(reviewPrompt(t, b, 'security'),    { phase: 'Review', label: 'review security',    agentType: 'tech-lead', schema: REVIEW }),
  ]).then((rs) => rs.filter(Boolean).flatMap((r) => r.blocking))

  phase('Review')
  let blocking = await reviewRound(build)
  for (let round = 0; round < 2 && blocking.length; round++) {          // bounded fix loop
    build    = await agent(fixPrompt(t, blocking), { phase: 'Review', label: 'address findings', agentType: 'js-dev', schema: IMPL })
    blocking = await reviewRound(build)
  }
  if (blocking.length) return { blocked: 'review', task: t.id, blocking }   // never reach the gate red

  phase('Verify')
  // Same bounded shape again: black-box QA against t.criteria → fix → re-verify, ≤2 rounds, then
  // `return { blocked: 'qa', task: t.id, qa }`.
}

phase('Gate')
return await agent(gatePrompt, { phase: 'Gate', label: 'mission-completion gate', agentType: 'qa-engineer' })
```

`sync-meta.js` turns that into the diagram — the reviews fan out as one group, the writers chain, and
everything inside the task loop is badged `repeat`:

```js
{ title: "Review", steps: [
  {"id":"review-1","label":"review correctness","agent":"tech-lead","repeat":true,"parallel":"g1"},
  {"id":"review-2","label":"review security","agent":"tech-lead","repeat":true,"parallel":"g1"},
  {"id":"review-3","label":"address findings","agent":"js-dev","repeat":true,"dependsOn":["review-1","review-2"]},
] },
```

There is no *Fix* phase, because a static DAG cannot draw a loop. The bounded `for`s and the
`return { blocked: … }` guards are what make the run honest, and they live in the code.

### Declare a round helper inside the loop that runs it

The extractor is **lexical**: a call is drawn where it is *written*, not where it is *invoked*.
`reviewRound` above sits inside the task loop, so its two `agent()` calls fall in the loop's range
and come out badged `repeat`, ordered after the build. Hoist that same helper above the loop and it
draws at its definition site instead — un-badged, sorted ahead of steps that really run before it
every iteration, so its `dependsOn` comes out backwards. Same program, wrong picture. Declare round
helpers where they run, or inline them.

## Writing step prompts

The agent already carries the persona — a step that runs `tech-lead` **is** the tech-lead. Don't
open with "You are Rio, the tech-lead…"; spend the prompt on the **task**:

- **What to do**, concretely — the change to build, the diff to review, the behaviour to verify.
- **The acceptance criteria** it is judged against, inline or by precise pointer
  (`the criteria in <mission>/tasks/<t>/task.yaml`); no stated definition of done produces work
  nothing can gate.
- **The context** — repo/branch (and *don't switch branches*), the load-bearing facts, the
  constraints (which suite, what must not regress, what must never reach the logs).
- **A `schema`**, so the result is structured data the next step can branch on — a review's
  `blocking` list, a QA `passed` flag. This is what lets the fix loop act on the result at all.

"Review the M2 build" gets an opinion; "review this diff against these three criteria, return
blocking vs nits" gets something the loop can use.

## Choose the cheapest node that does the job

A workflow is not a queue of agents. Most of what a pipeline does is not judgement, and paying an
LLM round trip for it is the single biggest waste in a run. In cost order:

1. **Plain JS** — free and instant. Dedupe, filter, branch, compose prompts, do budget maths. Never
   spend an agent on something the script can compute. Plain JS is not a diagram node, and that is
   correct: it is the absence of one.
2. **`workflow({ scriptPath }, args)`** — runs another workflow inline, no LLM at all. If you catch
   yourself writing a prompt that *asks a model to go and invoke a workflow*, that is this. Nesting
   is one level only.
3. **One batched command node** — shell work reaches the outside world only through an agent, so
   batch it: one `agent` call on `haiku` marked `kind: 'command'` that runs N commands and reports
   what they printed. Twelve board writes are one node, not twelve.
4. **A full agent** — judgement only: building, reviewing, verifying. Tier it — `{ model, effort }`
   — cheap and fast for mechanical steps, the strong model for the plan and the gates.

```js
await agent(
  ['Run exactly these, then report the lines they printed. Do nothing else.', '', ...commands].join('\n'),
  { phase: 'Build', label: 'tick 7 criteria', agentType: 'project-manager', model: 'haiku', kind: 'command' },
)
```

**The sandbox is why this matters.** `require`, `process`, `fs` and `fetch` are undefined in a
workflow script and `import()` is blocked at parse, so fs, git, bash and MCP are reachable *only*
through an agent — and discovery cannot happen inside the run at all. Resolve what the pipeline
needs first and hand it in:

```bash
node .claude/skills/mission-planner/scripts/mission-input.js M2 [--campaign <slug>]
```

That is what lets **one shared pipeline** at campaign level serve every mission, instead of a
generated copy per mission that drifts. A mission points at it with a
`workflows/<slug>/workflow.json` holding `{ "uses": "../../../../workflows/implementation" }`, and keeps
its own `runs.jsonl`. `uses` is relative to the pointer's OWN folder, which sits four levels under
the campaign (`missions/<mission>/workflows/<slug>`) — hence four `..`. A pointer that resolves
outside the board, or onto a folder with no `workflow.js`, is a validate failure.

## The body is a dynamic program

The diagram is a static picture; the body is a **dynamic workflow script**, and its most effective
shapes are ones the picture cannot hold — a `pipeline()` over a work-list discovered at run time, a
loop that spawns finders until two rounds come up empty, a fleet sized to the token budget. **Do not
shrink the workflow to what the diagram can draw**: the drawing is generated afterwards, and it
collapses a run-time fan-out into one badged node on purpose.

### Choosing the concurrency primitive

- **`for … await` (fully sequential)** — the ONLY safe shape for steps that **write files**. Writers
  share one tree and one branch; two at once corrupt it. This is the Octobots constraint (§ *Designing
  the run* 3), not a general preference.
- **`pipeline(items, stageA, stageB, …)` — the default for read-only multi-stage work.** Each item
  flows through all stages independently, **no barrier between stages**, so item A can be in *verify*
  while item B is still in *review*; wall-clock is the slowest single chain, not the sum of stages.
  Almost always what you want over a hand-rolled `for` of `parallel`s.
- **`parallel(thunks)` — a barrier.** Awaits everything before returning; use it only when the next
  step needs *all* results at once (dedupe across findings, early-exit on zero). A failed thunk
  resolves to `null`, so **`.filter(Boolean)`** before you use the results.

Never `pipeline`/`parallel` over writers. The moment a step writes, it sequences.

### Three shapes worth knowing

- **Verify adversarially, not with a single vote.** One reviewer is the weak link: plausible-but-wrong
  findings survive and real ones get one set of eyes. For a gate that must be trusted, spend the
  concurrency on **independent skeptics** — N verifiers per finding, each prompted to *refute* it and
  defaulting to "refuted" when unsure, keeping the finding only if a majority fail to refute. Where a
  finding can fail more than one way, give each verifier a distinct lens instead of N identical ones.
- **Don't enumerate what you can't count.** For find-every-X work, enumerated steps miss the tail.
  Loop until it runs dry — `while (dry < 2)`, dedupe each round against everything `seen` (never
  against "confirmed"), and consider a final critic that asks what's missing.
- **Scale to the token budget.** `budget.total` / `budget.remaining()` expose the turn's target, so
  size the fleet from it rather than hard-coding one. Guard on `budget.total`: it is `null` (and
  `remaining()` is `Infinity`) when no target is set, so an unguarded loop runs to the 1000-agent cap.

### Body constraints (these bite at run time)

- **`args` arrives as a JSON STRING, not an object. Parse it once, at the top.**

  ```js
  const ARGS = typeof args === "string" ? JSON.parse(args || "{}") : (args || {})
  ```

  Reading `args.base` directly gives `undefined` — silently. Three runs in one day went wrong this
  way and **every one reported success**: a fix merged into an already-merged branch because
  `args.base` fell through to a stale default, a run "fixed" a bug that had been excluded because
  the filter matched nothing and so filtered nothing, and scoped runs silently ran the whole list.
  Nothing threw. (Verified 2026-08-12: `typeof args` is `"string"` before and after an `await` — the
  value is intact, just never parsed.) And **do not write the defensive guard** —
  `(typeof args !== "undefined" && args && args.base) || "…"` converts a detectable bug into a silent
  one, since `undefined.base` would have thrown. Parse once, read from `ARGS`, let a missing key be
  missing.

- **No `Date.now()`, `Math.random()`, or argless `new Date()`.** They are unavailable and **throw** —
  they would break resume. Pass timestamps through `ARGS`; vary a per-item prompt by index, not
  randomness.
- **Write for resume.** `Workflow({ scriptPath, resumeFromRunId })` replays completed `agent()` calls
  from cache, but only when prompts and ordering are stable across runs.
- **Failure isolation.** A dead `agent()` inside `parallel`/`pipeline` becomes `null`, not a throw —
  `.filter(Boolean)` before use, and a transient API death is not a task failure (resume past it).
- **Keep `{ phase }` and `{ label }` literal.** They are read without executing the script, so
  `{ phase: someVar }` cannot be resolved and a computed label renders as `…`. `validate.js` reports
  both rather than drawing a step nobody can name.
- **No silent caps.** Concurrency is throttled to ~`cores−2`, one `parallel`/`pipeline` call takes
  ≤4096 items, and the run is capped at 1000 agents. If you bound coverage (top-N, sampling),
  **`log()` what you dropped** — a silent cap reads as "covered everything".

## The authoring loop

Scripts live in the `mission-planner` skill's `scripts/` directory (one home for everything that
writes the board). Run them from the repo root.

1. **Scaffold** — creates the folder and a runnable body:

   ```bash
   node .claude/skills/mission-planner/scripts/add-workflow.js \
     --campaign <campaign-slug> [--mission <mission-slug>] \
     --name "<name>" [--description "<one line>"]
   ```

2. **Write the body.** This is the whole design. Annotate every call with `phase`, `label` and
   `agentType`.

3. **Generate the picture** (`--all` instead of a directory does every workflow on the board):

   ```bash
   node .claude/skills/mission-planner/scripts/sync-meta.js <workflow-dir>
   ```

4. **Validate, and fix everything it reports:**

   ```bash
   node .claude/skills/mission-planner/scripts/validate.js <workflow-dir>
   ```

   It checks that `workflow.js` is present, that `meta` is locatable and a pure literal, that the
   **body parses**, that `meta` is **up to date with the body**, and that every `agent()` call names
   an **`agentType`** — the one that silently runs your whole workflow on the default subagent when
   it is missing. It also checks that **`meta.name` equals the folder slug**, which is the one part
   of `meta` that can still drift: `name` is authored once by `add-workflow.js` and `sync-meta.js`
   deliberately *preserves* it rather than regenerating it, so renaming the folder leaves the two
   disagreeing and no amount of re-running `sync-meta.js` will fix it — edit the `name` to match.
   Validating a `campaign.yaml` or `mission.yaml` also checks every workflow beneath it.

Do **not** write `runs.jsonl` by hand — `mission-execution` appends entries with `add-run.js` after a
run. It is a log, not a plan.

## Finishing

Before you hand back:

- `sync-meta.js` has been run since your last edit to the body, and `validate.js` is clean on the
  workflow **and** on its parent `mission.yaml` / `campaign.yaml`.
- Every `agentType` names something in `.claude/agents` (or the user explicitly chose otherwise).
- You have told the user, in a sentence or two: the phases, what runs in parallel, which agents you
  used and where you found them, and anything you deliberately left out.

Then point at the next step: **`mission-execution`** runs it and logs the run.
