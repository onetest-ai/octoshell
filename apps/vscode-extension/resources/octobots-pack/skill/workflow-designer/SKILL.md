# workflow-designer

You turn a **planned** board into a **plan of execution**: which agents run, in what order, and what
runs in parallel. You sit between the two other skills:

```
mission-planner     what work exists      (missions, tasks, acceptance criteria)
      ↓
workflow-designer   how it will run       (phases, agents, parallelism)   ← you are here
      ↓
mission-execution   run it, log the run
```

You do **not** decompose work into missions and tasks — that is `mission-planner`. You do **not**
run the workflow — that is `mission-execution`, which hands `workflow.js` to Claude Code's
`Workflow` tool.

## When a workflow is worth writing

A workflow is a real artifact with a real maintenance cost. Write one when the *sequence* is worth
recording, not merely because a mission exists.

**Write one when:**

- the mission's tasks have a genuine shape — a review gate, a fan-out, a build-then-verify order —
  that a person would otherwise have to re-derive each run;
- several tasks can run **concurrently** and you want that stated rather than discovered;
- the same sequence will run more than once (a campaign that ships mission after mission);
- different steps want **different agents**, and picking them per-run is guesswork.

**Don't write one when:**

- the mission is a handful of independent tasks with no ordering — `mission-execution` already
  composes a mission loop for that, and a board workflow would just restate it;
- you'd be inventing structure to look thorough. YAGNI applies here as hard as it does to tasks.

If you decide against one, **say so and why**. Silence reads as an oversight.

## The two levels

- A **campaign** workflow orchestrates that campaign's **missions**. A campaign may hold several.
- A **mission** workflow orchestrates that mission's **tasks**. **A mission has at most one** —
  `add-workflow.js` refuses a second, and `validate.js` reports it.

Design at the level you were asked about. A campaign workflow whose steps are individual *tasks* is
at the wrong altitude; so is a mission workflow whose steps are whole missions.

## Resolve the agents first — never invent them

A step's `agent` names a real agent. **Before designing anything, find out what exists:**

```bash
ls .claude/agents          # the repo's agents, one directory per agent
```

**The Octobots pack installs no agents at all** — it ships skills and a session hook. Every agent
name you can use comes from the repo itself, and many repos have none. So:

1. **Use names that exist.** A step naming an agent the repo doesn't have produces a script that
   fails at run time, and the board will happily show it as valid — `validate.js` checks the shape
   of the graph, not whether an agent is installed.
2. **If the repo has no suitable agent**, do not quietly substitute a plausible-sounding role
   (`implementer`, `tester`, `reviewer` are *examples in documentation*, not agents). Tell the user
   what the workflow needs and let them decide: install an agent, name an existing one, or use the
   generic default. Ask once, with the list you found.
3. **Prefer fewer, real agents over a rich cast of imaginary ones.** A three-step workflow that runs
   beats a seven-step one that doesn't.

Every `<a real agent>` in the example below is a placeholder for exactly this reason — there is no
default roster to fall back on.

State which agents you found and which you used. That sentence is what makes the workflow auditable.

## Designing the graph

1. **Read the board first.** `list.js` for the tree; the mission's `mission.md` for its tasks and
   acceptance criteria. The tasks are your raw material — a workflow that ignores them is fiction.
2. **Group tasks into phases.** A phase is a stage a person would name: *Plan*, *Build*, *Verify*,
   *Review*, *Ship*. Keep it to a handful; a phase per task is not a design.
3. **Mark what runs concurrently.** Steps sharing a `parallel` group id run together. Two tasks are
   parallel only if they truly don't touch the same files — concurrent edits to one tree is the
   failure this board exists to prevent. When in doubt, sequence them.
4. **Add dependencies only where real.** `dependsOn` names step ids that must finish first. Phase
   order already sequences phases, so you only need `dependsOn` for a dependency *within* the
   natural order — e.g. a review that waits on both halves of a parallel build.
5. **Put the gates in.** If a stage must not proceed on red (a QA pass, a review), make it its own
   phase so the shape is visible in the diagram.
6. **End a mission workflow at the gate, not at the last merge.** Landed tasks are not a green
   mission: per-task gates check per-task criteria, and nothing has yet verified the *mission's*
   acceptance criteria or exercised the tasks together. Give the design a final phase that flips the
   mission `done` and runs the **`mission-completion-gate`** (black-box QA against the mission
   criteria, the live/E2E pass, and a whole-mission review). Static gates between tasks, **one
   dynamic gate per mission** — a workflow whose last phase is "merge" is unfinished.

Every step carries `id`, `agent` and `label`. `id` is unique across the whole workflow. `label` is
what a human reads on the diagram — write it as an action (`Build task`, `Review the diff`), not a
restated agent name.

## The file format

A workflow is a folder holding two files:

```
.octobots/campaigns/<campaign>/workflows/<slug>/workflow.md   # description + ## Runs log
.octobots/campaigns/<campaign>/workflows/<slug>/workflow.js   # the executable script
.octobots/campaigns/<campaign>/missions/<mission>/workflows/<slug>/…
```

`workflow.js` is a **Claude Code dynamic-workflow script** — the thing `mission-execution` hands to
the `Workflow` tool. Its `export const meta` block is the board's source of truth for the diagram:

> **`meta` must stay a pure object literal** — no variables, function calls, spreads or template
> interpolation. Octoshell reads it *without executing the script*, so the moment it stops being a
> literal the workflow shows as unreadable in the app. The body below `meta` is ordinary code and
> may do anything.

```js
export const meta = {
  name: 'build-tasks',                       // must equal the folder slug
  description: 'Drive each task to a merged PR',
  phases: [
    { title: 'Plan',   steps: [{ id: 's1', agent: '<a real agent>', label: 'Decompose' }] },
    { title: 'Build',  steps: [{ id: 's2', agent: '<a real agent>', label: 'Build task' }] },
    { title: 'Review', steps: [
        { id: 's3', agent: '<a real agent>', label: 'Review correctness', parallel: 'r', dependsOn: ['s2'] },
        { id: 's4', agent: '<a real agent>', label: 'Review security',    parallel: 'r', dependsOn: ['s2'] } ] },
    { title: 'Gate',   steps: [{ id: 's5', agent: '<a real agent>', label: 'Mission gate', dependsOn: ['s3','s4'] }] },
  ],
}

// Body: phase() / agent() / parallel() / pipeline(). Loops and conditionals are fine here.
phase('Plan')
const tasks = await agent('decompose the mission', { schema: TASKS })

for (const t of tasks) {                       // tasks touch one tree — sequence them
  phase('Build')
  const built = await agent(`implement ${t.id}`, { phase: 'Build' })
  phase('Review')                              // read-only reviewers: safe to fan out
  await parallel([
    () => agent(`review ${built} for correctness`, { phase: 'Review' }),
    () => agent(`review ${built} for security`,    { phase: 'Review' }),
  ])
}

phase('Gate')
return await agent('run the mission-completion-gate', { phase: 'Gate' })
```

**Note what is parallel and what is not.** The *reviews* fan out (`parallel: 'r'` in `meta`,
`parallel()` in the body) because they only read a finished diff. The *builds* do not: tasks share one
working tree and one branch, so `parallel()`/`pipeline()` over tasks would put two `git checkout -b` in
the same tree and corrupt it — the exact failure step 3 above warns about. Fan-out is for **read-only**
agents; anything that writes files gets sequenced.

Note also that the body enters **every phase `meta` declares** — Plan, Build, Review, Gate. That is the
rule below, demonstrated: if the body had only entered `Build`, the diagram would be advertising three
phases that never run.

Step fields: `id`, `agent`, `label` (required); `parallel` (group id), `dependsOn` (step ids),
`backend` (`claude` | `copilot` | `codex`, when a step must run on a specific CLI).

**Keep `meta.phases` in step with the phases the body enters.** The board draws `meta`; the tool runs
the body. If they drift, the diagram lies.

## The authoring loop

Scripts live in the `mission-planner` skill's `scripts/` directory (one home for everything that
writes the board). Run them from the repo root.

1. **Scaffold** — creates the folder, a `workflow.md` and a runnable single-phase `workflow.js`:

   ```bash
   node .claude/skills/mission-planner/scripts/add-workflow.js \
     --campaign <campaign-slug> [--mission <mission-slug>] \
     --name "<name>" [--description "<one line>"]
   ```

2. **Add each step** — upserts into `meta`, rewriting only that literal and leaving the body alone:

   ```bash
   node .claude/skills/mission-planner/scripts/set-step.js \
     --workflow .octobots/campaigns/<c>/missions/<m>/workflows/<w> \
     --phase "Build" --id s2 --agent <agent> --label "Build task" \
     [--parallel b] [--depends-on s1,s2] [--backend codex]
   ```

   Re-running with the same `--id` replaces that step, wherever it currently sits — that is how you
   edit or move one.

3. **Write the body.** `add-workflow.js` leaves a `phase('Run')` stub. Edit `workflow.js` below the
   `meta` block so the code actually enters the phases you declared. Never hand-edit `meta` — use
   `set-step.js`, so a malformed literal can't silently break the board's diagram.

4. **Validate, and fix everything it reports:**

   ```bash
   node .claude/skills/mission-planner/scripts/validate.js \
     .octobots/campaigns/<c>/missions/<m>/workflows/<w>/workflow.md
   ```

   It checks: `workflow.js` present; `meta` locatable and a pure literal; `meta.name` equal to the
   folder slug; at least one phase; no empty phase; every step has `id`/`agent`/`label`; no duplicate
   step id; every `dependsOn` names a real step; no `parallel` group spanning phases. Validating a
   `campaign.md` or `mission.md` also checks every workflow beneath it, and flags a mission with more
   than one.

Do **not** write `## Runs` by hand — `mission-execution` appends entries with `add-run.js` after a
run. It is a log, not a plan.

## Finishing

Before you hand back:

- `validate.js` is clean on the workflow **and** on its parent `mission.md` / `campaign.md`.
- Every `agent` names something in `.claude/agents` (or the user explicitly chose otherwise).
- You have told the user, in a sentence or two: the phases, what runs in parallel, which agents you
  used and where you found them, and anything you deliberately left out.

Then point at the next step: **`mission-execution`** runs it and logs the run.
