# workflow-designer

You turn a **planned** board into a **plan of execution**: which agents run, in what order, and what
runs in parallel. You sit between the two other skills:

```
mission-planner     what work exists      (missions, tasks, acceptance criteria)
      ↓
workflow-designer   how it will run       (phases, agents, parallelism)   ← you are here
      ↓
mission-execution   run it, log the run
```

You do **not** decompose work into missions and tasks — that is `mission-planner`. You do **not**
run the workflow — that is `mission-execution`, which hands `workflow.js` to Claude Code's
`Workflow` tool.

## When a workflow is worth writing

A workflow is a real artifact with a real maintenance cost. Write one when the *sequence* is worth
recording, not merely because a mission exists.

**Write one when:**

- the mission's tasks have a genuine shape — a review gate, a fan-out, a build-then-verify order —
  that a person would otherwise have to re-derive each run;
- several **read-only** steps can run concurrently (parallel reviewers, parallel analyses) and you
  want that stated rather than discovered;
- the same sequence will run more than once (a campaign that ships mission after mission);
- different steps want **different agents**, and picking them per-run is guesswork.

**Don't write one when:**

- the mission is a handful of independent tasks with no ordering — `mission-execution` already
  composes a mission loop for that, and a board workflow would just restate it;
- you'd be inventing structure to look thorough. YAGNI applies here as hard as it does to tasks.

If you decide against one, **say so and why**. Silence reads as an oversight.

## The two levels

- A **campaign** workflow orchestrates that campaign's **missions**. A campaign may hold several.
- A **mission** workflow orchestrates that mission's **tasks**. **A mission has at most one** —
  `add-workflow.js` refuses a second, and `validate.js` reports it.

Design at the level you were asked about. A campaign workflow whose steps are individual *tasks* is
at the wrong altitude; so is a mission workflow whose steps are whole missions.

## Resolve the agents first — never invent them

A step's `agent` names a real agent. **Before designing anything, find out what exists:**

```bash
ls .claude/agents          # the repo's agents, one directory per agent
```

**The Octobots pack installs no agents at all** — it ships skills and a session hook. Every agent
name you can use comes from the repo itself, and many repos have none. So:

1. **Use names that exist.** A step naming an agent the repo doesn't have produces a script that
   fails at run time, and the board will happily show it as valid — `validate.js` checks the shape
   of the graph, not whether an agent is installed.
2. **If the repo has no suitable agent**, do not quietly substitute a plausible-sounding role
   (`implementer`, `tester`, `reviewer` are *examples in documentation*, not agents). Tell the user
   what the workflow needs and let them decide: install an agent, name an existing one, or use the
   generic default. Ask once, with the list you found.
3. **Prefer fewer, real agents over a rich cast of imaginary ones.** A three-step workflow that runs
   beats a seven-step one that doesn't.

Every `<a real agent>` in the example below is a placeholder for exactly this reason — there is no
default roster to fall back on.

State which agents you found and which you used. That sentence is what makes the workflow auditable.

## Designing the graph

1. **Read the board first.** `list.js` for the tree; the mission's `mission.yaml` for its tasks and
   acceptance criteria. The tasks are your raw material — a workflow that ignores them is fiction.
2. **Group tasks into phases.** A phase is a stage a person would name: *Plan*, *Build*, *Verify*,
   *Review*, *Ship*. Keep it to a handful; a phase per task is not a design.
3. **Mark what runs concurrently — and almost nothing is.** Steps sharing a `parallel` group id run
   together. **Only read-only steps may share one** (several reviewers on a finished diff, parallel
   analyses). Anything that writes files — a build, a fix round, a board update — is **sequenced**,
   even when two tasks look independent: every mission runs in the **one root working tree** on one
   branch, so concurrent writers corrupt it. There is no worktree escape hatch (see
   `mission-execution` § *Non-negotiable principles*); the answer to "these could run in parallel" is
   to order them. **The default is sequential; `parallel` is the rare exception, not the resting
   state.** If you find yourself adding a `parallel` group to a build step, stop — you almost
   certainly want a dependency instead.
4. **Chain writers so the diagram tells the truth.** `dependsOn` names step ids that must finish
   first. When several steps in a phase write files, chain them **linearly** — each `dependsOn` the
   step *before it* (`t2`←`t1`, `t3`←`t2`), not all hanging off one common ancestor (`t2`←`t1`,
   `t3`←`t1`). A fan-out from a shared parent draws on the diagram as **parallel branches**, so the
   board tells every reader those steps run concurrently — a lie for writers, and one the diagram
   keeps repeating. The picture must match the sequenced run. Only add a *cross* dependency (a review
   that waits on both halves of a genuinely parallel, read-only fan-out) where one is real.
5. **Put the gates in.** If a stage must not proceed on red (a QA pass, a review), make it its own
   phase so the shape is visible in the diagram.
6. **Design the not-green path — a workflow is not a sunny-day DAG.** A real run surfaces review
   findings and QA bugs; a plan that only draws Build → Review → Verify → Gate quietly assumes each
   passes on the first try, and that optimism makes a run read as done when it isn't. The remediation
   lives in the **body**, not `meta` (a static DAG can't draw a loop): after a review that returns
   blocking findings, loop *dev addresses each finding + adds the regression test → re-review*,
   bounded (≤2 rounds); after a QA failure, loop *dev fixes → re-verify*, bounded; and if it is
   **still** red after the bound, **stop and `return { blocked: … }`** instead of walking on to the
   gate. The diagram keeps the same phase shape — Review and Verify are where "what if it's red?" is
   answered, in code. A workflow with a single pass through review and QA and no branch for their
   findings is not a plan, it is a wish. See `mission-execution` § *The mission loop* for the bounds.
7. **End a mission workflow at the gate, not at the last merge.** Merged tasks are not a green
   mission: per-task gates check per-task criteria, and nothing has yet verified the *mission's*
   acceptance criteria or exercised the tasks together. Give the design a final phase that flips the
   mission `done` and runs the **`mission-completion-gate`** (black-box QA against the mission
   criteria, the live/E2E pass, and a whole-mission review). Static gates between tasks, **one
   dynamic gate per mission** — a workflow whose last phase is "merge" is unfinished.

Every step carries `id`, `agent` and `label`. `id` is unique across the whole workflow. `label` is
what a human reads on the diagram — write it as an action (`Build task`, `Review the diff`), not a
restated agent name.

## The file format

A workflow is a folder built around its script:

```
.octobots/campaigns/<campaign>/workflows/<slug>/workflow.js   # the executable script (meta + body)
.octobots/campaigns/<campaign>/workflows/<slug>/runs.jsonl    # append-only run log (created on first run)
.octobots/campaigns/<campaign>/missions/<mission>/workflows/<slug>/…
```

`workflow.js` is a **Claude Code dynamic-workflow script** — the thing `mission-execution` hands to
the `Workflow` tool. Its `export const meta` block is the board's source of truth for the diagram:

> **`meta` must stay a pure object literal** — no variables, function calls, spreads or template
> interpolation. Octoshell reads it *without executing the script*, so the moment it stops being a
> literal the workflow shows as unreadable in the app. The body below `meta` is ordinary code and
> may do anything — and it usually should do far more than the static diagram can draw. See
> **The body is a dynamic program** below.

```js
export const meta = {
  name: 'build-tasks',                       // must equal the folder slug
  description: "Drive the mission's tasks to a gated, verified done",
  phases: [
    { title: 'Plan',   steps: [{ id: 's1', agent: '<a real agent>', label: 'Decompose the mission' }] },
    { title: 'Build',  steps: [                                     // two writers → CHAINED, not parallel
        { id: 's2', agent: '<a real agent>', label: 'Build task A', dependsOn: ['s1'] },
        { id: 's3', agent: '<a real agent>', label: 'Build task B', dependsOn: ['s2'] } ] },
    { title: 'Review', steps: [                                     // read-only → the one real fan-out
        { id: 's4', agent: '<a real agent>', label: 'Review correctness', parallel: 'r', dependsOn: ['s3'] },
        { id: 's5', agent: '<a real agent>', label: 'Review security',    parallel: 'r', dependsOn: ['s3'] } ] },
    { title: 'Verify', steps: [{ id: 's6', agent: '<a real agent>', label: 'Black-box QA vs criteria', dependsOn: ['s4','s5'] }] },
    { title: 'Gate',   steps: [{ id: 's7', agent: '<a real agent>', label: 'Mission-completion gate',  dependsOn: ['s6'] }] },
  ],
}

// Body: phase()/agent()/parallel()/pipeline(). The loops and conditionals ARE the design — this is
// where a review's findings and a QA failure get ADDRESSED, not assumed away.
phase('Plan')
const tasks = await agent(planPrompt, { schema: TASKS })     // [{ id, brief, criteria }]

for (const t of tasks) {                        // writers share one tree — strictly sequential
  phase('Build')
  let build = await agent(buildPrompt(t), { phase: 'Build', schema: IMPL })

  // reviewers only READ the diff, so they fan out; their blocking findings feed a bounded fix loop
  const reviewRound = (b) => parallel([
    () => agent(reviewPrompt(t, b, 'correctness'), { phase: 'Review', schema: REVIEW }),
    () => agent(reviewPrompt(t, b, 'security'),    { phase: 'Review', schema: REVIEW }),
  ]).then((rs) => rs.flatMap((r) => r.blocking))

  phase('Review')
  let blocking = await reviewRound(build)
  for (let round = 0; round < 2 && blocking.length; round++) {           // ← bounded fix loop
    build    = await agent(fixPrompt(t, blocking), { phase: 'Review', schema: IMPL })  // fix + add the regression test
    blocking = await reviewRound(build)
  }
  if (blocking.length) return { blocked: 'review', task: t.id, blocking }  // stop — never walk on to the gate red

  phase('Verify')
  let qa = await agent(qaPrompt(t), { phase: 'Verify', schema: QA })      // black-box against t.criteria
  for (let round = 0; round < 2 && !qa.passed; round++) {                 // ← bounded fix loop
    build = await agent(fixPrompt(t, qa.failures), { phase: 'Verify', schema: IMPL })
    qa    = await agent(qaPrompt(t), { phase: 'Verify', schema: QA })
  }
  if (!qa.passed) return { blocked: 'qa', task: t.id, qa }
}

phase('Gate')
return await agent(gatePrompt, { phase: 'Gate' })   // flip mission done + run the mission-completion-gate
```

**Note what is parallel and what is not.** The *reviews* fan out (`parallel: 'r'` in `meta`,
`parallel()`/`reviewRound` in the body) because they only read a finished diff. The *builds* do not:
`s2`→`s3` are **chained** in `meta` and sequential in the body, because tasks share one working tree
and one branch — `parallel()`/`pipeline()` over writers would put two `git checkout -b` in the same
tree and corrupt it, the exact failure steps 3–4 above warn about. Fan-out is for **read-only** agents;
anything that writes files gets sequenced and drawn as a chain.

**Note where the not-green path lives.** `meta` has no *Fix* phase — a static DAG can't draw a loop.
The remediation is in the **body**: the bounded `for` loops re-run the fix-and-re-check, and the
`return { blocked: … }` guards stop the run rather than marching a red build into the gate. The
diagram stays Build → Review → Verify → Gate; the body is what makes it honest.

Note also that the body enters **every phase `meta` declares** — Plan, Build, Review, Verify, Gate. If
the body had only entered `Build`, the diagram would advertise four phases that never run.

Step fields: `id`, `agent`, `label` (required); `parallel` (group id), `dependsOn` (step ids),
`backend` (`claude` | `copilot` | `codex`, when a step must run on a specific CLI).

**Keep `meta.phases` in step with the phases the body enters.** The board draws `meta`; the tool runs
the body. If they drift, the diagram lies.

## Writing step prompts

The `agent` already carries the persona — a step that runs `tech-lead` **is** the tech-lead, and the
agent knows it. Do **not** open a prompt with "You are Rio, the tech-lead…"; the role-play is noise
the agent already has. Spend the prompt on the **task**:

- **What to do**, concretely — the change to build, the diff to review, the behaviour to verify — not
  a restatement of the agent's job title.
- **The acceptance criteria** it is judged against — inline, or a precise pointer to read them
  (`the criteria in <mission>/tasks/<t>/task.yaml`). A step with no stated definition of done produces
  work nothing can gate.
- **The context it needs** — repo/branch (and *don't switch branches*), the one or two load-bearing
  facts, the constraints (which suite to run, what must not regress, what must never reach the logs).
- **A `schema`**, so the result is structured data the next step can branch on — a review's
  `blocking` list, a QA `passed` flag — not prose the body has to parse. This is what lets the fix
  loop above act on the result at all.

Clear task in, structured verdict out. "Review the M2 build" gets you an opinion; "review this diff
against these three criteria, return blocking vs nits" gets you something the loop can use.

## The body is a dynamic program

`meta` is a **static picture** — a fixed set of phases drawn before the run. The body is a **dynamic
workflow script**, and its most effective shapes are ones the picture cannot hold: a `pipeline()` over
a work-list discovered at run time, a loop that spawns finders until two rounds come up empty, a fleet
sized to the token budget. **Do not shrink the workflow to what the diagram can draw.** Draw the
phases as the *coarse shape* (Build, Review, Verify, Gate) and let the body decide, at run time, how
many agents run inside each and in what fan-out. Keep `meta.phases` matching the phases the body
*enters* — not the agent count inside them. The diagram is the map, not the territory.

### Choosing the concurrency primitive

- **`for … await` (fully sequential)** — the ONLY safe shape for steps that **write files**. Writers
  share one tree and one branch; two at once corrupt it. This is the Octobots constraint (§ *Designing
  the graph* 3–4), not a general preference.
- **`pipeline(items, stageA, stageB, …)` — the default for read-only multi-stage work.** Each item
  flows through all stages independently, **no barrier between stages**, so item A can be in *verify*
  while item B is still in *review*. Wall-clock is the slowest single chain, not the sum of stages.
  Use it for "review each of N files, then verify each finding" — anything read-only with more than
  one step per item. It is almost always what you want over a hand-rolled `for` of `parallel`s.
- **`parallel(thunks)` — a barrier.** Awaits everything before returning; use it only when the next
  step genuinely needs *all* prior results at once (dedupe across findings, early-exit on zero). A
  failed thunk resolves to `null`, so **`.filter(Boolean)`** before you use the results.

Never `pipeline`/`parallel` over writers. Fan-out is for read-only agents; the moment a step writes,
it sequences.

### Verify adversarially, not with a single vote

One reviewer is the weak link — plausible-but-wrong findings survive and real ones get one set of
eyes. For a gate that must be trusted, spend the concurrency on **independent skeptics**:

- **Adversarial** — N verifiers per finding, each prompted to *refute* it (default to "refuted" when
  unsure); keep the finding only if a majority fail to refute.
- **Perspective-diverse** — when a finding can fail more than one way, give each verifier a distinct
  lens (correctness, security, does-it-reproduce) rather than N identical ones.

```js
const survives = (await parallel(
  ['correctness', 'security', 'reproduce'].map((lens) => () =>
    agent(refutePrompt(finding, lens), { phase: 'Verify', schema: VERDICT }))
)).filter(Boolean).filter((v) => !v.refuted).length >= 2
```

### Discovery: don't enumerate what you can't count

For unknown-size work — find every X, audit, migrate — enumerated steps miss the tail. Loop until it
runs dry (K empty rounds), dedupe against everything seen, and consider a final critic that asks
"what's missing?":

```js
let dry = 0, seen = new Set()
while (dry < 2) {                                  // stop after 2 empty rounds, not a fixed count
  const fresh = (await findRound()).filter((x) => !seen.has(key(x)))
  if (!fresh.length) { dry++; continue }
  dry = 0; fresh.forEach((x) => seen.add(key(x)))  // dedupe vs seen, never vs "confirmed"
}
```

### Scale to the token budget

`budget.total` / `budget.remaining()` expose the turn's token target — scale depth to it instead of
hard-coding a fleet. Guard on `budget.total`: it is `null` (and `remaining()` is `Infinity`) when no
target is set, so an unguarded loop runs to the 1000-agent cap.

```js
const FLEET = budget.total ? Math.floor(budget.total / 100_000) : 3
while (budget.total && budget.remaining() > 50_000) { /* one more finder */ }
```

### Body constraints (these bite at run time)

- **No `Date.now()`, `Math.random()`, or argless `new Date()`.** They are unavailable in a workflow
  script and **throw** — they would break resume. Pass timestamps via `args`; vary a per-item prompt
  by its index, not by randomness.
- **Write for resume.** `Workflow({ scriptPath, resumeFromRunId })` replays completed `agent()` calls
  from cache — but only when prompts and ordering are stable across runs. Keep prompts deterministic
  and the loop order fixed, so a stalled mission resumes instead of restarting from zero.
- **Failure isolation.** A dead `agent()` inside `parallel`/`pipeline` becomes `null`, not a throw —
  `.filter(Boolean)` before use, and a transient API death is not a task failure (resume past it).
- **Tier the models.** `agent(…, { model, effort })` — run mechanical build/PR steps on a cheaper,
  faster model and reserve the strong one for the plan and the review/verify gates. Biggest cost lever
  as the suite grows; the gate stays strong, so correctness is unaffected.
- **No silent caps.** Concurrency is throttled to ~`cores−2` at a time, one `parallel`/`pipeline` call
  takes ≤4096 items, and the run is capped at 1000 agents. If you bound coverage (top-N, sampling),
  **`log()` what you dropped** — a silent cap reads as "covered everything".

## The authoring loop

Scripts live in the `mission-planner` skill's `scripts/` directory (one home for everything that
writes the board). Run them from the repo root.

1. **Scaffold** — creates the folder and a runnable single-phase `workflow.js`:

   ```bash
   node .claude/skills/mission-planner/scripts/add-workflow.js \
     --campaign <campaign-slug> [--mission <mission-slug>] \
     --name "<name>" [--description "<one line>"]
   ```

2. **Add each step** — upserts into `meta`, rewriting only that literal and leaving the body alone:

   ```bash
   node .claude/skills/mission-planner/scripts/set-step.js \
     --workflow .octobots/campaigns/<c>/missions/<m>/workflows/<w> \
     --phase "Build" --id s2 --agent <agent> --label "Build task" \
     [--parallel b] [--depends-on s1,s2] [--backend codex]
   ```

   Re-running with the same `--id` replaces that step, wherever it currently sits — that is how you
   edit or move one.

3. **Write the body.** `add-workflow.js` leaves a `phase('Run')` stub. Edit `workflow.js` below the
   `meta` block so the code actually enters the phases you declared. Never hand-edit `meta` — use
   `set-step.js`, so a malformed literal can't silently break the board's diagram.

4. **Validate, and fix everything it reports:**

   ```bash
   node .claude/skills/mission-planner/scripts/validate.js \
     .octobots/campaigns/<c>/missions/<m>/workflows/<w>/workflow.js
   ```

   It checks: `workflow.js` present; `meta` locatable and a pure literal; `meta.name` equal to the
   folder slug; at least one phase; no empty phase; every step has `id`/`agent`/`label`; no duplicate
   step id; every `dependsOn` names a real step; no `parallel` group spanning phases. Validating a
   `campaign.yaml` or `mission.yaml` also checks every workflow beneath it, and flags a mission with more
   than one.

Do **not** write `runs.jsonl` by hand — `mission-execution` appends entries with `add-run.js` after a
run. It is a log, not a plan.

## Finishing

Before you hand back:

- `validate.js` is clean on the workflow **and** on its parent `mission.yaml` / `campaign.yaml`.
- Every `agent` names something in `.claude/agents` (or the user explicitly chose otherwise).
- You have told the user, in a sentence or two: the phases, what runs in parallel, which agents you
  used and where you found them, and anything you deliberately left out.

Then point at the next step: **`mission-execution`** runs it and logs the run.
