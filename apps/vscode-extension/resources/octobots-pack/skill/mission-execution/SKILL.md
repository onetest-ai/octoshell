# mission-execution

How to take a **planned octobots mission** (tasks each with acceptance criteria — see the
`mission-planner` skill for planning) and drive it to a **verified, merged mission**. It is the loop
that reliably lands dozens of tasks green: each task planned, built test-first, independently QA'd and
review-gated before it lands, then the whole mission gated: the mission's last Mission QA task runs the test cases live, and the gate runs them again, with a live E2E that
catches defects the green unit suites miss.

**Use this when:** executing a mission's tasks (plan exists, criteria set). **Don't** use it for a
trivial one-off edit — that's just an edit.

## Branch topology

**All of it happens in the repo you were opened in** — the root checkout, with its `.octobots/`
board, its installed skills and its installed dependencies. Never a git worktree, never a second
clone (see *ONE working tree* under **Non-negotiable principles**). Isolation comes from
**branches**, not from a second directory.

There are **two levels of PR**, and both are required. Tasks integrate into the mission's feature
branch; the mission integrates into `main`:

- **Mission → a feature branch** off `main` (`feat/<campaign-slug>-m<n>`) — **this is the branch a
  mission lives on.** Its tasks PR into it, and the **mission gate runs here**.
- **Task → a short-lived branch off the mission branch** (`feat/<campaign-slug>-m<n>-t<k>`) **plus a
  small PR back into the mission feature branch.** One task, one small PR, reviewed and merged before
  the next task starts.
- **The per-mission PR is the feature branch → `main`**, opened only after the mission gate is green.
  This is the PR a human reviews as a coherent unit; `main` never sees a half-built mission.

> **Both, not either.** Small task PRs keep each diff reviewable while the mission is being built;
> the mission PR is what actually lands the work on `main`. Skipping the task PRs makes the final
> diff unreviewable; skipping the mission PR puts ungated work on `main`.

For a multi-mission **campaign** that must land as one unit, add a campaign branch
(`feat/<campaign-slug>`) between them: missions PR into it and it merges to `main` once at the end.
Default to mission → `main` unless the campaign genuinely must ship atomically.

> **The branch name is load-bearing.** Tokenomics attributes cost to a mission by finding the
> **campaign slug** and an **`m<n>`** token in the branch name — a branch named `mission/<slug>` matches
> nothing and the mission's cost lands nowhere. Keep the shape above, or declare the real names in the
> mission's `mission.yaml` `tokenomics.branches` list (see `mission-completion-gate`).

So throughout the loop the **base is the mission feature branch**: cut each task branch off it,
review and merge that task's small PR back into it, and sit the tree on it between tasks. When the
last task has merged and the mission gate is green, the feature branch PRs to `main`.

**Keep the task PRs small.** Small is the entire point — a task PR a reviewer can hold in their head
in one sitting. If a task's diff is sprawling, that is a planning signal, not a reason for a bigger
PR: split the task on the board (`mission-planner`) rather than merging a diff nobody can review.
Small PRs also mean a bad task is reverted on its own instead of unpicked from a mission-sized
commit.

## No `Workflow` tool, no `workflow.js`: the orchestrator dispatches sub-agents

**Missions are executed by direct sub-agent dispatch (the `Agent` tool), not by the `Workflow`
tool.** Do not run a board `workflow.js` and do not compose a dynamic Workflow script for a mission.
If a mission or campaign folder still holds a `workflows/*/workflow.js`, treat it as **historical
reference only**: you may read it for the order its author intended, but you execute that order with
`Agent` calls from the main loop.

Why this replaced workflows: a script can only *ask*. The workflow failures recorded in the project's `CLAUDE.md` / `AGENTS.md`
are all the same failure — a long command that never finished, a model that was never pinned,
`null` results, cwd drift, and resume caches invalidated by prompt edits. Each one needed a structural
patch inside the script. Direct dispatch removes that layer. The orchestrator sees every result as
it arrives and decides the next step, and a crashed agent is simply dispatched again. There is no run
cache to keep byte-identical.

## The mission loop (orchestrator + one sub-agent per phase)

The main loop is the **orchestrator**. It walks the mission's tasks in board order. For each task it
dispatches **one sub-agent per phase, one at a time, in the foreground**, reads the result, and only
then dispatches the next phase. It never builds anything itself.

```
mission start   set-status.js … "M<n> - name" active; cut feat/<campaign-slug>-m<n> off main, push it
for each task in board order:            # strictly sequential: one tree, one branch
  set-status.js <mission-dir> "T<m>.<k> - …" active
  [0] Plan     Agent(tech-lead,  model: opus)    only when the task has no tactical plan yet
  [1] Build    Agent(python-dev | js-dev, model: sonnet)
  [2] Review   Agent(tech-lead,  model: opus)    remediates blocking findings in place
  [3] QA+land  Agent(qa-engineer, model: sonnet) re-verifies, checks off ACs, flips status, merges
  stop the mission on any BLOCKED verdict; do not dispatch the next task onto a broken base
all tasks merged → set-status.js … "M<n> - name" done → mission-completion-gate (see below)
```

### Dispatch rules (each one exists because the workflow version broke it)

1. **Always pass `model:` explicitly.** The role definitions in `.claude/agents/*` pin
   `model: sonnet`, and the agent definition beats the parent's model. Use `opus` for plan and review,
   and `sonnet` for build, QA and land.
2. **Foreground, sequential, never background for build work.** Dispatch one writer at a time and wait
   for its result. A sub-agent that writes files (build, fix, land) must never run alongside another
   writer in the shared tree. Read-only agents, for example two reviewers on one finished diff, may
   run in parallel: send them in one message.
3. **Sub-agents cannot spawn sub-agents.** A dispatched agent has no `Agent` tool. Never ask one to
   "consult Rio" or "ask the dev". If a reviewer has questions for the dev, it **returns** them; the
   orchestrator **relays** them: it dispatches the dev with those questions, then dispatches the
   reviewer again with the answers.
4. **Every brief ends with a required verdict block.** The `Agent` tool has no schema, so the brief
   must demand a final fenced JSON block. For example, build returns
   `{"tests_pass":bool,"branch":"…","pr_url":"…","blocked":bool,"reason":"…"}`; review returns
   `{"final_state_green":bool,"blocking_findings":[…],"fixed":[…],"questions_for_devs":[…]}`; land returns
   `{"passed":bool,"merged":bool,"pr_url":"…","notes_written":bool,"criteria":[{"n":1,"evidence":"…"}]}`.
   The orchestrator treats `notes_written:false` as BLOCKED. A missing or
   unparseable block counts as **BLOCKED**, never as green.
5. **Pin cwd and scope searches.** Every brief begins with the absolute repo path, tells the agent to
   `cd` there, says "the brief below is authoritative — do NOT read or search the board", and scopes
   searches to the subproject or source directories the task touches. Never search from the repo root.
6. **Use the fast test lane by default.** Read the project's declared test lanes before briefing a
   build (`AGENTS.md § Test lanes`; where a project has not declared them yet, use the project's
   documented commands in its `CLAUDE.md` / `AGENTS.md`). Brief the agents with those commands by name,
   never with a command of your own:
   - **Scoped tests** while building: the fast lane's scoped form, on the files the task touches.
   - **Full suite**: the fast lane, parallel and without coverage.
   - **Only the mission gate's coverage run uses the coverage lane**, which is slower and serial.
   - Portability: macOS has no `timeout` binary. Use the Bash tool's own timeout, or
     `perl -e 'alarm shift; exec @ARGV' N cmd`.
7. **Long commands: foreground with `timeout: 600000`, never `run_in_background`.** Name the lane
   command in the brief. Never background a test command: the only exceptions are
   non-terminating servers and watchers (rule 11 says how to start those). If the agent could not watch a command finish, it returns `blocked:true`. Budget per agent:
   build runs **scoped** tests only; the full fast lane runs at the QA + land step, which also waits for
   the PR's CI checks (`gh pr checks --watch`) before merging, where the project has CI. Functional
   verification is manual QA against the mission's test cases.
8. **Do not re-introduce the agent to itself.** `subagent_type` loads the persona. The brief carries
   the task (title, description, acceptance criteria verbatim, branch names, base branch), the
   constraints and the evidence required.
9. **One review round + one fix round per task.** Define "blocking" in the review brief (AC unmet,
   reproducible defect, or security exposure with a PoC). Anything else is filed as a board bug.
   Keep separate counters for question rounds and fix rounds.
10. **A dead agent is a dispatch to retry, not a task failure.** If an agent returns an API or transport
    error, inspect `git status` and the branch, keep committed work, and dispatch again with "resume:
    these commits already exist, do not redo them". Resume from the board and git, never from a cache.
11. **Servers and QA environments: detach, poll, and go through `qa-env.mjs`.** Start a server with
    `nohup ... > log 2>&1 < /dev/null &`, so it holds no terminal and cannot block the tool call, then
    poll readiness with a bounded `curl -m 2` loop (a fixed number of tries, each capped at 2 seconds)
    and fail the step when it never answers; never wait on the server unbounded. For example, 30
    tries: `for i in $(seq 1 30); do curl -fsS -m 2 -o /dev/null http://127.0.0.1:<port>/ && break;
    [ $i = 30 ] && exit 1; sleep 1; done`. QA server, migration
    and seed commands run through `qa-env.mjs <db> -- <cmd...>`, which reads `.octobots/qa-env.json`,
    refuses a database name the project did not declare as a QA one, and exports the declared
    environment variables, so a QA run can never touch a real database. The script is
    `.claude/skills/mission-execution/scripts/qa-env.mjs`. A project with no database has no
    `.octobots/qa-env.json`, and its QA servers start directly.

### The phases

**Every task runs the same phase sequence.** The ordering is deliberate: the last thing that happens
before a merge is always **independent verification**, never the author's own claim.

0. **Plan** *(conditional — usually skip it)* — `tech-lead` (Rio) produces a short, decisive tactical
   plan: the exact files, the reuse-first approach, a concrete **test_list**.
   **Skip this phase when the mission's plan document already carries per-task tactical detail** —
   exact files, test code, implementation sketch — **and a tech lead has already reviewed it.** In
   that case re-planning is not caution, it is an invitation to deviate from the reviewed design;
   point the builder at the plan section instead and tell it to raise a concern rather than silently
   improvise. **Add this phase** when tasks are specified only by a title and acceptance criteria.
1. **Build** — `python-dev` (Py) and/or `js-dev` (Jay), **TDD**. Cuts the task branch, writes the
   failing test, implements, gets suites + type-check + lint green, commits incrementally with
   **scoped staging**, pushes, and opens the small PR into the mission feature branch.
   It does **not** check off criteria, flip status, or merge — all three belong to QA.
   For a cross-stack task, dispatch the devs **sequentially on one branch** (backend first, then
   frontend), never at the same time.
2. **Review gate** — the in-house **`tech-lead` review** (`requesting-code-review` / `code-review`)
   over the task's full diff against its base (`git diff <mission-feature-branch>...HEAD`) with a
   **security lens** on anything touching untrusted input / auth.
   **The reviewer remediates in-flight.** For each blocking finding it fixes the code itself, adds
   **the regression test that would have caught it**, re-runs the suites green, and commits onto the
   task branch. It returns the findings *and what it did*, plus `final_state_green`. This is faster
   than a round trip to the dev and keeps the finding and its fix in one head — but it means a
   non-empty findings list is **not** by itself a failure. Gate on `final_state_green`, and relay the
   findings either way. (Handing the fix back to a dev is still valid; it is a cost trade, not a
   correctness one.)
   > **Optional external review gate.** If the project has an external code-review bot available (e.g.
   > GitHub Copilot via the `await-copilot-review` skill), add it as an extra pass before the merge
   > — treat its findings like any review-gate finding (fix + regression test + re-verify). It is not
   > required; the in-house tech-lead review is the gate.
3. **QA + land** — `qa-engineer` (Sage) **re-verifies from scratch**, taking neither the dev's nor
   the reviewer's word: re-runs the real suites, lint and type-check, then checks **each** acceptance
   criterion and demands concrete evidence for it — a named test, an observed value. *A criterion
   with no evidence is a fail, not a pass.* On green it **first writes a `## QA verification` block
   into the task's `notes`** (via `entity-io.mjs` `loadEntity`/`dumpEntity`, never by appending raw
   text). The block records:
   - the verdict and the PR;
   - the **pre-existing record** the checks ran on;
   - **per criterion**, the test name AND the observed value from its own probe;
   - the reviewer's fixes, and any test gaps found.

   Then it checks off **exactly the criteria it verified**, flips the task's `status`, commits that
   `task.yaml`, and **merges the PR**. A ticked criterion with no matching evidence line in `notes` is
   a defect in the land step. The board, not the chat, is where a later reader looks for how a task
   was proven. On red it does **not** merge; it reports precisely and stops.
   **Before declaring the task done, run `impact --diff` (`knowledge-explorer`) and account for
   every row** — either the file changed too, or say why it doesn't need to. A row left unaddressed
   is not a maybe; it's the next task's surprise.

Running QA **after** the review, and giving it the merge, is what makes the gate real: the agent
that verifies is the agent that lands, and it saw the reviewer's fixes as part of what it verified.

> **When the board is gitignored.** Many repos keep `.octobots/` out of git (it is the working
> board, not source). Then the criteria-checkoff and status flip are **local-only edits with nothing
> to commit** — say so in the QA prompt, because an agent told to "commit the board change" and
> finding nothing staged will reach for `git add -A`, which is the one thing this loop forbids
> absolutely. Where the board **is** tracked, commit those edits alongside the task's work.

**Capture tokenomics (non-blocking).** Once the mission is green and flipped `done`, collect the
run's cost/effort record — `node .octobots/tokenomics/run.mjs` (the CLI ships with the pack), or
the *Octobots: Export Tokenomics Report* command — and commit the refreshed
`.octobots/tokenomics/` artifacts. **This is the last moment the data exists:** agent transcripts
live outside the repo, run to tens of megabytes per session, and are pruned without warning. Once
they are gone the mission's cost is unrecoverable.
> **Never blocks.** This is analytics; a failure here is a note, not a stop. Do not hold a green
> mission open because collection failed.

**Resuming a stalled mission** needs no run id. Read the board (which tasks are `done`) and the
mission branch (`git log`, open PRs). Then dispatch the phase that did not finish for the first
unfinished task, telling the agent what already exists.

### Mission QA: run the test cases live

**The last-task convention.** A mission's final task is `Mission QA: run tests/m<n> live…`, owned by
QA (`role: qa-engineer`), and it runs the whole suite in `tests/m<n>/`, not a slice. Its own acceptance
criteria restate the mission's. It is the only live run outside the gate: build tasks still gate
statically. The canonical rules are in `mission-completion-gate` § *QA on the test
cases*; this task and gate phase 2 apply the same ones, and they must stay in step:

- Run every TC in `tests/m<n>/` against the real system, by the mode each TC names.
- Write `runs/RUN-YYYY-MM-DD-NNN.md`, one section per TC with the steps run and the observed values.
- Record each TC as PASS, FAIL, BLOCKED or UNREACHABLE. UNREACHABLE is written as status `blocked`, with the reason in the RUN file.
- Could not drive the browser or log in is BLOCKED, not a pass.
- A manual execution (F5 or a human) is noted as manual in the RUN file.
- Name the pre-existing record per criterion; a criterion proved only on QA-created data is not passed.
- Write `## QA verification` into the task and mission `notes` through `entity-io.mjs`. The gate writes its own `## Completion gate (<date>)` section, never a second `## QA verification`.
- Tick exactly the criteria that have evidence: the task's own. Do not tick the mission's; record which mission criteria have evidence in the `## QA verification` block, and the gate ticks them in phase 5.
- Call `set-test-status.js` for every TC run, installed at `.claude/skills/mission-planner/scripts/set-test-status.js`:
  PASS -> `pass`, FAIL -> `fail`, BLOCKED and UNREACHABLE -> `blocked` (the reason in the RUN file). It writes the
  frontmatter `status` and `last_run: {date, evidence}` only, and is safe to repeat. Example:
  `node .claude/skills/mission-planner/scripts/set-test-status.js .octobots/campaigns/<c>/tests/m<n>/TC-003_<slug>.md pass --evidence .octobots/campaigns/<c>/tests/m<n>/runs/RUN-2026-10-06-001.md`.
  Never edit the status by hand. A legacy TC (no `status`, `kind` or `mission`) is first run through `set-test-status.js <tc-file> --migrate`.

## Three loops: when the tests run again

A mission is not executed once. The same dispatch machinery runs three different loops, and the
orchestrator picks the one that matches what it was asked to do, never the first one that comes to hand:

- **Implementation** — building the mission's planned tasks. This is the task loop above: plan, build,
  review, QA + land, one task at a time, ending in the mission gate.
- **Testing** — implementation is done, or a later mission has landed and the acceptance criteria need
  re-running. Dispatch `qa-engineer` to re-run the mission's tests and re-check each criterion against
  the code as it is now. Nothing is built in this loop; a failure becomes a board bug, not an inline edit.
- **Fixing** — bugs have accumulated on this mission and are being worked off. Dispatch a dev per bug,
  test-first (the failing regression test comes before the fix), then re-run the testing loop over the
  affected criteria before the bug is marked fixed. A bug fix is a change like any other: it still goes
  through review, then QA + land, before it merges.

Re-run the tests at the boundary of each loop: after every build and fix round (scoped, fast lane), at
QA + land (the full fast lane), and again after any later mission lands on the same code. A green run
from before the change is not evidence about the code after it.

## QA depth follows blast radius

Not every task deserves the same gate. The variable is not how hard a task was, nor how "critical"
it feels — it is **how much later work silently inherits the defect if this task is subtly wrong.**

A task whose output nothing consumes can only be wrong about itself. A task that defines a
boundary, a type, a convention or a parse is wrong about *everything built on it*, and everything
built on it will still pass its own tests. That asymmetry, not effort, is what QA depth should
track. Applying one depth to every task is simultaneously **wasteful on the leaves and
insufficient on the foundations** — and you pay for the second half at the mission gate, after
several tasks have built on the bad answer.

### Identifying a foundation task

**The declared signal, available at planning time.** Every task in a plan carries an interface
block: *Consumes* what earlier tasks produced, *Produces* what later tasks rely on. **A task whose
`Produces` appears in any later task's `Consumes` is a foundation task.** That is structural and
decided before anyone knows which task will break — no judgement, no labelling a task "critical"
after it has already cost you a day.

**The undeclared signals**, for coupling nobody wrote down. Treat a task as foundational when it:

- **defines a type or data shape** others construct or destructure (`Edge`, `Config`, `Spine`);
- **establishes a convention** others must independently re-apply — a weighting rule, a path
  normalisation, a sort order. This is the most dangerous kind, because the coupling exists only
  in the authors' heads;
- **is the only thing touching an external boundary** — git, the filesystem, a network, a clock.
  Everything downstream trusts its parsing and cannot check it;
- **produces persisted output** — a committed artifact, a migration, a cache. The error outlives
  the run that made it;
- **sits early in a pipeline.** Position correlates with blast radius; the first stage feeds every
  later one.

**The diagnostic that settles it.** Ask: *if this task's output were subtly wrong — not crashing,
just wrong — how many later tasks would still pass their own tests?* If the answer is "most of
them", it is a foundation task. Crashing defects are cheap; they announce themselves. **Plausible
defects are the expensive ones,** and they are exactly what a foundation task emits.

### What the deeper gate actually is

Not "more tests" and not "run the suite again". **Black-box verification against the built
artifact** — the same thing the mission gate does, moved earlier for tasks that have earned it:

1. Build the package.
2. Write throwaway probes in a temp directory that import the **built output**, not the source.
3. Drive it with inputs the unit tests never construct — a real temp repo, a real config layout, a
   real hostile filename.
4. Never read `src/` and never read the existing tests. Reading them makes you re-derive the
   author's assumptions, which is the one thing you are there not to do.
5. Delete the probes. They are not deliverables.

Leaf tasks keep the static gate: suites, lint, type-check, acceptance criteria by inspection, the
review.

### The floor: every review walks the criteria

Black-box probing is the escalation. **The minimum, on every task including leaves, is that the
review reads the acceptance criteria and, for each one, finds the code that satisfies it and
challenges it** — *"criterion 2 says X; this is the code that would do it; does it?"*

That is one question per criterion and it costs almost nothing, but it is a different question from
the ones a reviewer asks by default. Correctness, determinism, conventions and security are all
questions about the *code*; none of them notices that the task was for something the code never
does. A diff can be clean by every code-shaped measure and still not implement its criterion.

Two failure shapes it catches that a quality review misses:

- **A criterion with no code behind it.** Nothing in the diff addresses it. Trivially findable by
  walking the list, invisible if you only read the diff top to bottom.
- **Code that satisfies the criterion's words but not its intent** — the criterion named no input
  class, so handling one and dropping four still reads as satisfied.

Where a criterion cannot be mapped to code, that is a finding to report, not a puzzle to solve
quietly: either the criterion is unimplemented, or it is not phrased as a contract and nobody can
verify it. Both belong back with the planner.

### A type annotation is not a fact about runtime data

At any seam where data arrives from outside the program — a file read back off disk, a network
response, a parsed document — the type says what you *intend* to receive, and the runtime says what
you *actually* received. Treating the first as evidence about the second is how a validated boundary
ships unvalidated.

It fails most quietly where the type cannot be represented at all. `Record<number, string[]>` is a
perfectly good TypeScript type and a claim JSON cannot honour: **JSON object keys are always
strings.** A guard written to defend that boundary checked every value and trusted the type for the
keys — because the type had already "guaranteed" them — and the malformed-document test table
enumerated eight cases that all varied the value axis and none that varied a key.

That is not carelessness. It is the predictable result of writing tests from *imagination*: an
author enumerates the failure modes that came to mind, and the ones that came to mind are the ones
the type did not appear to cover.

> **Write the guard's tests from the field list of `T`, not from the failure modes you thought of.**
> For every field: absent, null, wrong primitive type, wrong container shape, and — where the type
> claims something the wire format cannot express — the shape the wire format will actually deliver.

The tell that you are in this situation: a type whose guarantee the serialisation format cannot
carry. Integer keys in JSON. `Date` anywhere in JSON. A discriminated union whose tag is optional. A
tuple in YAML. Each is a place the compiler is confident and the runtime is not.

### The guard entry belongs to the task that introduces the rule

A source-level guard — a test asserting one spelling of a shared predicate, one helper for a rule
several modules need — only stays useful if it grows with the code. It will not, if it is treated as
something reviews add.

The failure is visible when a mission's own review keeps reporting *"the guard did not cover what
this very mission added"*: one task extracts a helper into a single spelling **and writes its
conventions entry**, while the same mission leaves a second shared rule spelled two ways. The
discipline gets applied retroactively — only to rules that have already caused a defect — so the
guard permanently lags the code by exactly one incident.

> **When a task introduces a predicate a second module will ask, or a helper a consumer will import,
> the guard entry is part of THAT task — not of the review that follows it.** A reviewer adding it
> is the system working late, not the system working.

This is cheap where it belongs and expensive everywhere else. The task's author knows the rule is
shared, because they extracted it. A reviewer three tasks later has to rediscover that, and a
reviewer three *missions* later finds it as a defect with a regression test attached.

### Green is not evidence

A passing suite means **the code satisfies the tests**. The tests were written by whoever wrote the
code, alongside or after it, from the same understanding — so green certifies *self-consistency*,
not correctness. It cannot tell you about a case nobody thought of, because the missing case is
missing from the tests too. The requirement lives in the acceptance criteria and nowhere else.

Every defect this loop has caught was green at the time:

- a manifest branch excluded by its own guard — 91 tests passing, none covering the three marker
  types the description named;
- a `localeCompare` sort whose order changes with `LANG`, churning a committed artifact on an
  environment change alone;
- a module edge with negative weight — an architectural dependency asserted from evidence of its
  own absence;
- a file name able to forge an entire commit record, including its timestamp.

So: **green is a precondition for looking, never a reason to stop.** Never cite "the suite passes"
as evidence for a criterion; it is evidence about the suite.

**Which makes the test suite an artifact under verification, not a source of truth.** QA owes it
the same scrutiny as the implementation, in this order — the order is what keeps the verdict
independent:

1. **Probe first, blind.** Verify each criterion against the built artifact without reading the
   tests or the source. Reading them first makes you re-derive the author's assumptions and you
   will confirm rather than test.
2. **Then map criteria to tests.** For each criterion, find the test that covers it. A criterion
   with **no** covering test is a gap even when your probe passed — nothing stops the next change
   from breaking it silently. Report it.
3. **Then read those tests adversarially.** Would this test fail against a plausibly wrong
   implementation, or does it restate what the code does? A test asserting the shape of the output
   it just computed proves nothing. So does a test whose fixture was reverse-engineered from a
   failing run.
4. **Check the negative and degenerate cases.** Absent-input, empty-input, malformed-input and
   boundary criteria are where defects live and where suites are thinnest.

### The two failure modes this catches, and how to avoid each

Green suites cannot catch either. That is the point.

**1. Code that never executes.** A guard no input satisfies, a branch excluded by an earlier
condition, a fallback whose predicate is always false. The tests pass because they exercise the
reachable paths, and the unreachable path reads perfectly.

> *Avoid it in review:* for every branch, guard and early return, ask **what input reaches this —
> and can any?** Reading code for correctness is not the same as reasoning about reachability. A
> condition no value satisfies is invisible to a correctness read and obvious to a reachability
> one.
> *Catch it in QA:* drive the built artifact with a whole realistic input class the tests never
> construct, and ask what it does — not whether a function returns the right value for a fixture.

**2. A shared premise that diverged.** Several modules each need one rule; most agree and one does
not. Each file is internally consistent, so every per-task review passes. The defect exists only
*between* the files, where no single-task review can see it.

> *Avoid it at design time:* any rule needed in two or more places gets **one named exported
> helper**, never a re-implementation. Open-coding the same expression in five files is not
> duplication to clean up later — it is five chances to disagree.
> *Catch it in review:* treat a **duplicated rule as a blocking finding**, not a nit. Ask "does
> this task re-implement something an earlier task already provides?"

### When the plan itself is the defect

Both of the above have shipped from a *reviewed* plan. A builder told to follow the reviewed design
faithfully will faithfully reproduce its bugs, and a reviewer reading the diff against that same
plan will confirm it matches. The plan is authoritative about **intent**, never about
**reachability or consistency** — those are properties of code, and only the code and the built
artifact can answer them. When a defect traces back to the plan, fix the plan **at source** before
the next task starts: derived copies (a mission's `design.md`, an agent's brief) are read by every
task still to come.

## The mission gate (where this loop ends)

**Landed tasks are not a green mission.** The loop above gates each task *statically* — suites,
coverage, its own acceptance criteria, a review of that task's diff. Nothing in it has yet verified
the **mission's** acceptance criteria, and nothing has exercised the tasks *together*. That is a
separate, blocking, once-per-mission step:

> **Static gates between tasks, ONE dynamic gate per mission** (the last Mission QA task runs the suite live once before it; the gate re-runs it).

When the last task's PR has merged, flip the mission `done` with `set-status.js`. That fires
`.octobots/hooks/mission-gate.mjs` (PostToolUse; it triggers on `M<n>` ids and deliberately ignores
`T<m>.<n>` task flips), which blocks and hands you the **`mission-completion-gate`** skill. Run it.
It adds what a per-task loop structurally cannot:

- **Black-box QA against the MISSION's criteria** — Sage never sees the diff or the source, and
  talks only to Alex (`ba`) and Rio (`tech-lead`). Per-task QA cannot substitute: it verified task
  criteria, with the developer's report in hand.
- **The live/E2E pass**, if the project gated tasks statically (the usual choice — see *Pacing*).
  Stand the real stack up and drive it from outside the process. This is the highest-value step and
  the one most often skipped, because every task "already passed".
- **A whole-mission review** over `git diff <base-branch>...<mission-feature-branch>` — where
  `<base-branch>` is the branch the mission was cut from (the campaign branch when the campaign lands
  atomically, else `main`). Diffing against `main` when a campaign branch is in use would pull in
  every prior mission already merged there, so the orchestrator passes the mission's base branch in the
  briefs it dispatches for each gate phase.
  This review catches integration defects, duplicated abstractions across tasks, and marker/doc
  coherence — invisible to a review scoped to one task's diff.

**Only then does the mission feature branch PR into `main`** — that PR is the per-mission PR, and it
is opened after the gate is green, never before. **Do not end a mission run when the last task has
merged** — that is the middle of the job, not the end of it.

## Non-negotiable principles

- **ONE working tree. No git worktrees — ever.** Everything a mission does happens in the workspace
  you were opened in, on branches. Do not create a git worktree, and do not accept a suggestion to
  "isolate the work" in one.

  A worktree only carries **tracked** files. It does not carry anything `.gitignore`d — and on a
  real project that is most of the working state: `node_modules`, `.env`, build caches, local
  databases, `.mcp.json`, `.claude/` (your installed skills), and **`.octobots/` itself** when the
  board is local-only. An agent in a worktree is looking at a repo with no board to drive, no skills
  to drive it with, and no dependencies installed. It will "succeed" while verifying nothing.

  > **Red flag: you are about to run `git worktree add`, or a tool offered to isolate your work.
  > Stop. Use a branch in the tree you are already in.**

- **The orchestrator is a writer in the shared tree too.** While a writer sub-agent is in flight,
  the main loop must not edit tracked files, switch branches, or commit. `git status` showing clean
  does **not** mean idle — it means *between* agent operations, and the next `git checkout` is
  already queued. A branch switch here is silently destructive: uncommitted edits made against one
  base reattach to another, and a later commit reverts the difference with no conflict to warn you.
  Work that is not part of the running mission — a pack edit, a doc fix, an unrelated bugfix —
  either waits for that agent to return, or is committed **without the working tree at
  all**: build the blobs and the commit with plumbing against a temp index
  (`GIT_INDEX_FILE=… git read-tree <branch>`, `git hash-object -w`, `git update-index`,
  `git write-tree`, `git commit-tree`, `git update-ref`), which never touches HEAD, the shared
  index, or a single file the agents are using. `.octobots/` writes are the exception when the
  board is gitignored — they are branch-independent and safe at any time.
- **Sequential, never parallel on the shared tree.** One mission in flight at a time, its tasks
  strictly ordered, and exactly one writer sub-agent dispatched at a time.
  Two concurrent `git checkout -b` in one working tree corrupts state. Since worktrees are off the
  table, **there is no escape hatch for "genuinely parallel" build work — sequence it.** Work that
  looks parallel (two tasks on unrelated files) is still ordered: the tree, the branch and the board
  are shared, and the ordering costs a few minutes where a corrupted tree costs the mission.
- **Flip the MISSION status, not just task statuses.** Mark the mission `active` before starting its
  first task, and `done` once the last task is green (the gate then ticks the mission's criteria in phase 5): `set-status.js <campaign>/missions/<mission> "<M<n> - name>" active|done`. This is
  not bookkeeping. A mission that is never flipped is never gated — and `.octobots/hooks/work-log.mjs`
  records the session → mission link that cost and effort attribution rely on. Flipping only task
  statuses silently skips both.
- **Board writes belong to the task that earns them.** The task's own **PR/merge step** checks off that
  task's acceptance criteria and flips its `status`, committing the `.octobots/` change on the
  task branch alongside the work it describes. Mission-level flips (mission `active` at the start, `done` at the end) are the
  orchestrator's, made on the mission branch **before the first task** and **after the last task lands**.
  Never let a task write board state for a *different* task, with one exception: the last Mission QA task writes `## QA verification` into the mission `notes`.
- **Acceptance-criteria-driven.** Every task carries ≥1 checkable criterion (set at plan time); the
  QA + land phase checks them off; the live E2E re-verifies the mission-level criteria.
- **Extensive testing.** TDD; full suites + the project's linters + type-checks green before a task
  lands; **a regression test for every bug and every review-gate finding** (the test that would have
  caught it).
- **Trust-but-verify.** A task lands on green and the mission auto-merges on green, but for
  **substantive** review-gate findings, verify the fix in the **landed mission-branch code** afterward —
  a green QA proves the tests pass, not that the specific concern was actually addressed.
- **The orchestrator routes; it never absorbs a role's work.** The main loop dispatching the agents
  quietly becomes the most expensive agent in the run the moment it does a specialist's job itself:
  driving the browser, trawling logs, sweeping greps, hand-verifying criteria. Delegate and keep only
  the finding. **Red flag: turns climbing while `subagent_dispatches` stays flat.** See *Pacing* for
  why this costs correctness, not just money.
- **Reuse-first; don't overcomplicate.** Prefer parameterizing/extending existing machinery over
  standing up a parallel system.
- **Design-first for non-trivial work.** A short design note (tech-lead, as its own gating first task —
  often a mission's first task) settles storage/migration/contract decisions before the build.
- **Scope review before building.** Have the `ba` + `tech-lead` review the mission's scope + criteria;
  surface gaps as a prioritized list and fix the plan before coding.
- **Live E2E at the mission gate** (e.g. Playwright), never per build task — see § *The mission gate*. The
  one other live run is the mission's last task (§ *Mission QA: run the test cases live*), after every
  build task has landed; the gate still runs the suite again. It
  catches prod-breaking bugs (case-sensitivity, install failures, UX defects) that green unit suites do
  not. When it finds defects, **file them as octobots bugs and fix them**; the mission isn't done until
  it's green.
- **Commit hygiene.** Follow the project's commit/PR conventions (e.g. the `Co-Authored-By` and
  generated-with trailers documented in `CLAUDE.md` / `AGENTS.md`).

## Failure recovery & git hygiene

- **Transient agent/API failure ≠ task failure.** When a sub-agent dies with a `Connection closed`/
  API error (not a logic failure), don't let it retry for hours: inspect the working-tree state, discard
  any **uncommitted** partial branch (preserving unrelated pre-existing edits), and **dispatch the failed phase again**.
  Completed phases are already on the branch and the board, so only the failed phase re-runs. Tell the
  re-dispatched agent not to redo work it already did. *(Verify before you clean: a "partial" file may be
  committed code from an earlier task — restore, don't delete, anything you didn't just create.)*
- **Commit incrementally so a crash is recoverable.** A dev agent that WIP-commits leaves *committed*
  state on the branch after a mid-run crash — not an uncommitted partial someone has to reconstruct by
  hand (and risk deleting real files while cleaning up).
- **Push the plan/board baseline before the first task lands.** A locally-committed-but-unpushed plan
  gets absorbed into the first task's commit (or squash-merge), forcing a divergence-reconciliation
  dance. Push the mission branch with its board baseline first, and push as tasks land, so the branch
  fast-forwards trivially and a crash never strands the plan.
- **Scoped staging, always.** `git add <exact paths>` / `git commit -- <paths>`, never `git add -A`/`.` —
  the shared tree may hold unrelated pre-existing edits (or another agent's work) that a bare add sweeps in.

## Pacing (confirm with the user once, up front)

- **Merge gate:** auto-merge-on-green vs pause-for-approval each merge.
- **Cadence:** roll straight through tasks vs checkpoint after each (or after the gating design task).
- **Isolation:** not a choice — **branches in the one working tree**, always (see the non-negotiable
  above). If a live dev server reading the tree is a problem, stop the server or point it at a build
  output; do not reach for a worktree.
- **QA depth:** live QA per task vs a **static gate** — gate each task on static checks (suites + lint +
  type-check + acceptance criteria by inspection + the review gate) and concentrate all live/dynamic
  verification into a dedicated hardening/E2E task or mission that re-verifies the criteria that were only
  inspected. Prefer the static gate when a mission has many build tasks that would each otherwise need the
  full stack stood up. In live QA, QA verifies against the **spec (BA + tech-lead), black-box — not by
  reading the implementation** (see the `qa-engineer` verification modes).
- **Model tiering (cost/latency):** run the mechanical phases — implementation/TDD and the PR/merge
  step — on a cheaper, faster model (e.g. `sonnet`), and keep the stronger model (e.g. `opus`) for the
  phases where judgment pays off: the tactical **plan** and the **review gate** (with its security lens).
  The review gate stays strong, so correctness is unaffected — this is the biggest lever when tasks slow
  down as the codebase + test suite grow. Set it on every `Agent` dispatch via the `model:` parameter.
- **Cost is not the same lever as delegation.** Model tiering prices `Agent` dispatches; it does not stop
  the orchestrator absorbing a role's work (the non-negotiable above). The distinction matters because
  some missions are genuinely expensive to verify — a browser UI needs real interaction. Pay that cost
  *through QA*: spending heavily because `qa-engineer` is exercising a live app is correct; spending
  the same because the orchestrator clicked through the app itself buys a worse result — no black-box
  perspective, no structured verdict, nothing reusable next mission. Watch `orchestrator_cost_pct`
  alongside the turns/dispatches tell: **41–52% is healthy delegation; 66–78% is the main loop having
  taken the work over.** When a mission needs live/browser verification, hand it to `qa-engineer` with
  a written brief and a structured verdict.

Default that works: auto-merge-on-green + roll-straight-through + branches-in-tree + a design-gate
checkpoint. Stop only on a blocker or a genuine product decision (use AskUserQuestion for those).
